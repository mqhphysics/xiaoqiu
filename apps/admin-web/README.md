# 晓球管理中心

项目内独立的 React + Vite 管理网站，复用晓球统一 NestJS API 和 PostgreSQL。公开网站仍为 `apps/mini-program`，管理站源码在本目录。

在本任务目录双击 **打开晓球管理中心.cmd**，页面打开后点击 **进入管理中心**，无需填写账号和密码。入口固定为 `http://127.0.0.1:5173/`，与原网站/微信启动文件并排。操作仍使用现有、有效的组织管理员身份，普通网站登录保持原有方式。

页面安排、常用操作和设计理由见[管理中心使用与设计说明](../../docs/guides/晓球管理中心使用与设计说明.md)。

无浏览器启动或指定现有 API：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-admin-center.ps1 -NoBrowser
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-admin-center.ps1 -NoBrowser -RequireAccountLogin
```

第二条是以后团队使用时的账号登录方式；更换方式前需关闭当前管理服务。启动器复用已就绪的当前工作树服务，不重复编译正在运行的原生数据库驱动。管理扩展在本机Vite服务内运行，调用原NestJS应用服务并连接同一数据库；其他公开/V2接口仍转发到已运行的API，修复前后端版本不一致的404，无需替换主目录API。默认需要准备数据服务时复用项目原启动器并传`-NoBrowser`，不传`-Seed`。其他工作树或运行方式占用5173时明确失败，不自动改变端口。

只有本地开发入口启用一键管理：服务绑定回环地址，进入请求检查本机地址、Host、Origin及同源请求；服务器确认配置的账号本来就有管理权限，再创建普通会话并记录审计。生产构建不会开放一键入口，客户端不包含管理员密码。自定义`ApiBaseUrl`时须同时配置匹配的`DatabaseUrl`，避免连接不同数据库。

手动开发使用 `.env.example` 对应的公开配置。生产构建必须配置实际 `VITE_API_BASE_URL`；Vite 本地 `/api` 代理不是生产 Nginx 的部署配置。`VITE_LOCAL_SHORT_PASSWORDS=1` 只影响开发环境登录表单，服务端仍独立决定是否允许本机短密码。

## 页面与可操作范围

| 模块       | 本轮能力                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------- |
| 工作台     | 当前组织真实待办计数、赛事概览及操作入口                                                           |
| 账号与权限 | 完整实名/学号/邮箱、资料编辑、每人真实活动/会话、组织冻结/封禁/恢复                                |
| 球队与球员 | 搜索、关联资料、完整学号及档案编辑，版本冲突保护                                                   |
| 赛事与比赛 | 既有赛季/赛事/球队/场地/赛程入口，V2名单审核、战报录入/审核/更正/历史对比、规程版本、晋级预览/确认 |
| 发布帖子   | 官方资讯/普通帖子，直接发布/待审核，最多9图上传和预览                                              |
| 帖子审核   | 状态筛选，编辑、批准、封禁、恢复，AI辅助审核配置状态                                               |
| 反馈与举报 | 反馈处理/回复、被举报内容处理及通知                                                                |
| 图片管理   | 本站实际文件预览，引用下架/恢复，版本化封禁记录及原图访问阻断                                      |
| 操作记录   | 本组织关键动作、稳定操作者和对象编号、安全变更摘要                                                 |
| 系统状态   | API/数据库、真实Outbox积压及失败记录；Worker活性、容量和备份没有证据时明确未确认                   |

组织/平台管理员可用组织模块；赛事管理员只操作获授权赛事。权限在服务器执行，前端入口限制只用于体验。

资料和规程写入包含修改原因、幂等键和版本基线；网络或5xx不确定时保存原请求，重试不重新生成一次操作。确认的战报不可原地覆盖，更正产生后续版本，历史确认版保留。

## 公开图片接线与AI适配

封禁状态使用既有AuditLog保存版本化策略，无schema变更。本站公开媒体接口检查策略并返回404，管理员的受控预览仍能读取原文件；不物理删除文件。恢复只还原尚未被新资料替换的引用，帖子相册被处理时先下架整组。外站文件不在可封禁清单内。

本机管理扩展识别本站旧媒体目录并只读其文件；新上传存入本工作树私有目录，并保存5173的绝对图片地址。主API需要加载本轮`media.service.ts`/`media.controller.ts`及`media-access-policy.ts`，兼容绝对地址相册并阻断旧直链。当前运行的3001还没有加载，能力查询会如实报告并在图片管理页显示提示。需授权集成与重启后才算日常接线完成。

后续AI服务由服务端环境变量`ADMIN_AI_MODERATION_URL`配置，可选`ADMIN_AI_MODERATION_KEY`作为Bearer凭据；变量由启动管理服务的进程继承，凭据不放前端。HTTP POST协议为`xiaoqiu-moderation-v1`，请求含`type`、`id`、`text`、`images`（实际文件的data URLs）、`version`，帖子还含`title`。服务须返回JSON `decision: ALLOW | REVIEW | BLOCK`和非空`summary`。20秒超时，错误响应不执行处理；结果为人工参考，不自动封禁。配置后的管理服务需重新启动。测试只使用本机模拟网关验证协议，尚无真实模型效果验收。

比赛缺少完整规程、有效阶段或锁定名单时，显示后台阻断原因。旧演示赛事只有摘要规程，不能将它当成完整V2试运行配置。赛事已经开始录入报告后，新规程迁移需要另行设计；当前受控发布入口收窄保护，避免把旧确认报告与最新规程直接混用。
