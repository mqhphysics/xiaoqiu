# 晓球信息管理现状与管理后台规划

> 状态：讨论草案，2026-09-26。本文记录当前已实现行为和后续构想；后台功能清单不表示已经开发或验收。

> 2026-10-01 复核：下文修正名单工作台挂接状态。最新进度与首轮真实赛事必做项见[总览](../status/项目进度总览-2026-10-01.md)；其余当时的数据库核对记录不视为本轮重新验收。

## 1. 现在的信息系统

晓球目前以 PostgreSQL 为事实来源。演示 Seed 提供 1 个组织、2 个赛季、16 支球队、224 名球员、36 场比赛和 8 个账号，覆盖普通学生、关联球员、队长、信息员、赛事管理员五类身份。H5 从 API 读取这些资料，页面不应自己再保存一套球队或球员事实。

| 对象                                  | 目前存放与用途                                                              | 谁可以看/改                                 |
| ------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------- |
| `Team`                                | 组织内球队代码、名称、学院、简介、颜色、临时队徽地址                        | 公开展示；目前没有完整的队徽编辑后台        |
| `PlayerProfile`                       | 稳定 ID、来源键、姓名、号码相关资料、位置、身高、年级、照片、头像、五维能力 | 公开资料由 API 输出；完整学号不在公开接口中 |
| `User`                                | 登录名、昵称、实名、完整学号、邮箱、账户头像与可选球员关联                  | 本人看本人；组织管理员实名目录查询被审计    |
| `RoleAssignment` / `TeamMembership`   | 组织、赛事、球队范围内的身份和队伍关系                                      | 服务端按范围校验，前端入口不是权限边界      |
| `TeamRegistration` / `RosterSnapshot` | 报名与已锁定版本的名单                                                      | 赛事管理流程维护；历史快照不能直接覆盖      |
| `MatchEvent` / `MatchAppearance`      | 进球、助攻、红黄牌、出场等比赛事实                                          | 赛季数据由这些事实计算，不能手工改页面数字  |

这次演示数据使用 10 位学号：`2023/2024/2025` + `99` 演示段 + 4 位唯一数字。数据库已核对 224 个演示球员学号互不重复、8 个演示账号学号互不重复。`99` 演示段只是本地约定，不能作为真实学校的学号规则。注册 API 目前校验 10 位数字；底层列仍允许更长字符串，已有导入流程也有自己的格式规则，因此正式录入规则应按组织配置并统一验证。

球队队徽、球员头像、账户头像和球员档案照是不同资料。当前示意队徽和照片来自 `apps/api/demo-media/`，API 返回本地图片地址。账户持有人更换账户头像不会同步改球员档案照片；球员头像另有现存上传入口。档案照片目前只由演示 Seed 填入，尚无正式上传、审核和版本流程。五维能力是独立演示值，与比赛事件计算出的出场和进球不是同一种数据。

## 2. 合理之处与当前缺口

现有组织隔离、稳定球员 ID、名单快照、角色范围、审计日志和公开/受限字段分离是合理的基础。公开球员 API 不返回完整学号；本人页和授权管理员目录是另外的读取路径。将 `User` 与 `PlayerProfile` 分开，也允许一个学生先作为用户加入，之后再认领球员档案。

当前仍是演示级系统：

1. 管理站 `apps/admin-web` 由赛程工作台作为入口，已包含“球队与名单核对”导航并挂接 `AdminRosterWorkspace`。名单页主要读取/核对，队长提交、管理员审批/锁定还没有完整写入流程；也没有统一的球队、球员、用户和媒体资料管理界面。
2. 队徽和照片只有 Seed/只读地址，没有正式的上传、裁剪、审核、来源与授权记录。16 张示意照片在 224 个球员中循环，不能被理解为真实身份验证。
3. 球员能力值没有评分人、测评规则、有效赛季、版本或复核状态；正式使用前需要定义来源和修改权限。
4. 学号、实名、球员认领和重复档案之间还缺少可操作的核验、冲突处理和撤销流程。不能仅凭姓名匹配或覆盖球员资料。
5. 队徽、球员档案照和五维能力虽已有存储与读取字段，但正式管理员写入 API、权限、版本、审计和幂等尚未实现。
6. 本地演示 Seed 会恢复演示凭据和部分演示资料。正式资料不得由 Seed 承载，部署到公网前要清除演示凭据和这些示意人物照片。

## 3. 管理后台的完整功能地图

后台应以“待办队列 + 全局检索 + 对象详情 + 变更历史”为骨架。列表支持组织/赛季/球队/状态筛选、字段列配置、保存视图与导出；详情页展示资料、关联记录、版本差异和操作日志。批量操作先预览影响，再提交。

### 3.1 赛事与组织

- 组织、学院、校区、场地、赛季、赛事、阶段、小组、轮次及规则配置；启停与归档。
- 球队报名审批、队伍代码与别名管理、队长和教练、颜色与正式队徽、赛季参赛关系。
- 赛程编排、发布预览、版本回滚建议、延期/取消说明、场地冲突检查。
- 比赛报告、阵容、换人、进球、助攻、牌、评分的录入与复核；比分和榜单重算预览。

### 3.2 人员与身份

- 用户目录：账户状态、实名与学号核验、邮箱验证、角色范围、禁用/解禁、登录设备与会话处理。
- 球员目录：姓名、球衣名、号码、主/副位置、惯用脚、身高、院系年级、简介、档案照与五维能力；按赛季查看球队归属和比赛数据。
- 认领流程：本人申请、证明材料的受限查看、管理员核对、冲突提醒、批准/驳回、解除关联与申诉。姓名相同不自动合并。
- 队伍成员关系：队长提名、离队/转队、跨赛季历史、报名与锁定名单差异。
- 重复档案候选列表、合并预览与人工决定；保留旧 ID 映射和审计链。

### 3.3 内容与运营

- 官方公告、赛事资讯、焦点推荐、图片及发布时间的编辑、预览、审核、撤回。
- 社区动态、评论、比赛评分、私信和举报的审核工作台；处理结果通知及申诉。
- 消息模板、站内通知、订阅消息计划和发送记录；仅对授权对象发送。
- 反馈工单、常见问题、赛事工作人员交接与批注。

### 3.4 资产、数据与系统

- 媒体库：上传/裁剪、用途区分（账号头像/球员头像/档案照/队徽/内容图）、作者与授权、审核、替换历史、过期与删除计划。
- 数据导入：字段映射、格式校验、去重候选、错误报告、试运行、审批、幂等提交；导出按权限脱敏。
- 数据质量：缺失照片、重复学号、异常位置、无球队关联、统计与事件不一致、即将过期的素材授权等看板。
- 权限和审计：角色矩阵、授权范围、敏感字段访问日志、管理员操作审计、变更前后差异、双人复核规则。
- 运维：任务队列、失败重试、Outbox 状态、备份/恢复演练、存储配额、错误监控、API 健康、发布版本与数据变更记录。
- 外部接入：将来对接校方身份、微信登录、对象存储、通知服务时使用适配器；记录同步来源、时间、失败与人工修正。

## 4. 关键操作流程

| 流程          | 必要步骤                                                                             |
| ------------- | ------------------------------------------------------------------------------------ |
| 新增球队      | 选组织和赛季 → 校验代码唯一 → 填基础资料与临时/正式队徽 → 预览 → 审批发布 → 记录版本 |
| 新增/认领球员 | 先查稳定 ID 与来源键 → 核验身份和同名冲突 → 关联用户 → 审批 → 对外发布可公开字段     |
| 替换档案照    | 上传本人授权素材 → 裁剪预览 → 审核归属与使用范围 → 新版本生效 → 保留旧版本的恢复窗口 |
| 导入名单      | 上传受限原件 → 映射与校验 → 显示新增/更新/冲突 → 人工确认 → 生成新名单版本           |
| 修正比赛      | 标明原因和证据 → 展示比分/榜单影响 → 权限复核 → 事务写入事件与审计 → 重算和通知      |

所有重要写操作都应在应用服务中完成组织隔离、角色与对象范围检查、幂等键、乐观版本和审计；图片或证明材料还需访问控制和保留期限。后台不能靠隐藏按钮限制权限。

## 5. 建议实施顺序与待定问题

1. **先打基础**：确认字段所有权、正式学号校验策略、图片与能力值的来源/审核模型；补管理员登录、导航、全局搜索和统一权限中间层。
2. **先做高频维护**：球队、球员、用户实名目录及认领、媒体库、报名/名单版本；在现有已挂接的赛程和名单核对页上补正式权限与写入流程。
3. **再做赛事运营**：比赛事件修正、统计重算、内容审核、消息、举报和数据质量看板。
4. **最后做跨系统与运维**：身份适配、对象存储、备份恢复、监控与高级报表。

需要产品负责人后续决定：谁有权批准球员认领与档案照；真实学号是否始终 10 位、是否允许其他年份；能力值由谁测评及何时重评；球员可自行修改哪些公开资料；肖像授权和撤回期限；跨赛季转队如何展示；正式队徽的提交、审核与知识产权归属。这些决定之后再定 API 契约与后台页面细节。

针对已经确认的首轮完整比赛目标，优先完成正式授权、真实赛事切换、名单提交/审批/锁定、信息员报告、管理员确认/更正和统计一致性；本章的能力测评、高级媒体库、全局检索与高级报表是后续规划，不全部作为首场比赛前置条件。上线前的基本备份与恢复仍必须完成，不能因为高级运维排在后面就省略。
