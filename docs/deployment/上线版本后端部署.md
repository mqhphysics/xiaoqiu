# 晓球上线版本后端部署

适用于本轮账号登录版的仓库源码。H5、管理后台、API、Worker 必须使用同一已验收提交。本文提供部署步骤，本轮没有连接或部署到任何真实服务器；执行记录见末尾。

## 1. 选择部署位置

后端可以运行在这台 Windows 电脑，也可以运行在自己的云服务器。已有 Sites H5 的浏览器直接访问配置的 HTTPS API，不要求 API 与 Sites 在同一台机器。建议先用独立试运行数据库验证，再以一台 Linux 云服务器部署 API、Worker、PostgreSQL、管理后台与 HTTPS 反代；H5 继续留在 Sites。

Windows 本机已核实有 Node.js 24.15.0、Docker Desktop Linux Engine、运行中的 PostgreSQL 17.4 容器，以及 `ssh`、`wsl`、`gh`。这些说明本地开发工具可用，不代表已具备公网可访问的 HTTPS 入口。`localhost`、`127.0.0.1` 和局域网地址不能作为所有 Sites 访客共用的 API 地址。没有创建隧道、改防火墙或查看服务器凭据；本机长期公网部署还需要用户提供已有的公网接入方式、域名和 TLS 配置。

开始实际部署前，只需确认以下非敏感信息：服务器系统与 CPU/内存/磁盘、是否已有 Docker Compose、API 与后台域名、是否有现成 HTTPS 反代、数据库选择本机容器或托管 PostgreSQL、备份保存位置、组织名称/组织代码，以及允许访问的 H5 域名。密码、私钥、数据库连接串不需要发在聊天里。

## 2. 运行依赖与容量

| 项目           | 本仓库固定基线                                                                | 说明                                                            |
| -------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Node.js 镜像   | `node:22.14.0-bookworm-slim`                                                  | 与现有 CI/Dockerfile 对齐；本机 Node 24.15.0 不是容器版本       |
| pnpm           | `11.5.2`                                                                      | 安装用 `--frozen-lockfile`，不自动更新锁文件                    |
| PostgreSQL     | `postgres:17.4-bookworm`                                                      | 现有迁移/CI 基线；数据库主版本升级单独验证                      |
| Prisma         | `6.19.3`                                                                      | 从锁文件安装，迁移使用仓库 CLI                                  |
| Nginx          | `nginx:1.27.4-alpine`                                                         | 管理后台静态资源容器                                            |
| Caddy（可选）  | `caddy:2.10.2-alpine`                                                         | 本文提供的 HTTPS 反代 profile                                   |
| Docker Compose | 使用支持 `service_healthy` / `service_completed_successfully` 的 Compose 插件 | 本次配置渲染使用本机 v5.5.0；不使用旧版 Python `docker-compose` |

这些是可重复构建的版本基线，不声称是各项目最新安全补丁。部署前检查官方安全更新，升级固定镜像后重新做迁移、角色、媒体与业务验收；记录实际镜像 digest，避免使用 `latest` 自动换版本。Node.js 支持周期以[官方发布表](https://nodejs.org/en/about/previous-releases)为准。

小规模赛事的初始预算可用 2 vCPU、4 GiB 内存、40 GiB SSD，并给媒体、数据库和备份另留空间；这是容量起点，尚未做并发压测。若直接在服务器构建全部镜像，建议 4 vCPU / 8 GiB 或在独立构建机器产出镜像再传入。负载增长时先观察数据库连接、磁盘、API 延迟与 Outbox 堆积。

## 3. 配置文件与实际功能边界

使用 [infra/release/compose.yaml](../../infra/release/compose.yaml) 和 [无秘密模板](../../infra/release/.env.example)。不要拿日常 `infra/compose.yaml` 替代正式配置；release 栈默认项目名 `xiaoqiu-release`、独立数据库 `xiaoqiu_release`，不会改日常 PostgreSQL/H5 端口。

release 包含数据库、迁移、API、Worker、管理后台和可选 `edge` 反代。数据库不映射宿主端口；API 默认 `127.0.0.1:3101`，后台默认 `127.0.0.1:5180`。只在明确准备好域名/HTTPS 的服务器上启动 `edge`。Compose 在健康数据库之后运行迁移，迁移成功才启动业务服务；这一启动约束对应 [Docker 官方说明](https://docs.docker.com/compose/how-tos/startup-order/)。

当前最小 release 栈沿用 PostgreSQL 镜像的 `POSTGRES_USER` 初始化账号，该账号实际具有数据库超级用户权限，且迁移/API/Worker 共用它；**这不是已经完成的最小权限生产配置**。公开真实数据前，建议使用专用应用角色（仅访问自己的库/schema）和受控迁移角色，或采用已有托管 PostgreSQL + Coolify 配置。需要由数据库运维创建角色、核对 Prisma 所需对象权限及连接串，重新验收迁移和所有写入；本文没有改用户机器权限，也没有把虚构的角色分离参数写成现成能力。

| 配置                            | 含义/设置方式                                                                    |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `COMPOSE_PROJECT_NAME`          | 固定部署实例名；改变它会使用另一组数据卷                                         |
| `APP_VERSION`                   | 已审查 Git commit，兼作应用镜像标签和健康响应版本                                |
| `POSTGRES_USER` / `POSTGRES_DB` | 此实例数据库用户与库名，使用模板默认值即可                                       |
| `POSTGRES_PASSWORD`             | 必填；在目标机器生成，建议 64 位十六进制串，避免数据库 URL 转义问题              |
| `DEFAULT_ORGANIZATION_ID`       | 安全初始化返回的真实组织 UUID，不使用 DEMO UUID                                  |
| `DEFAULT_TOURNAMENT_ID`         | 可先空；建立并发布真实赛事后填赛事 UUID，再更新 API                              |
| `CORS_ORIGINS`                  | 逗号分隔的精确浏览器 Origin，例如 Sites H5 与后台；不带路径/尾部斜杠，不用通配符 |
| `VITE_API_BASE_URL`             | 后台**构建时** API 地址，需带 `/api`，例如 `https://api.example.edu/api`         |
| `API_DOMAIN` / `ADMIN_DOMAIN`   | Caddy 使用的域名，不带 `https://` 和路径                                         |
| `ACME_EMAIL`                    | 证书运维联系邮箱，仅 `edge` 使用                                                 |
| `WORKER_*`                      | 模板给出代码实际支持的并发、轮询、租约、事务超时和重试配置；先保留默认           |

Compose 将 `NODE_ENV=production` 固定传给 API/Worker。`LOCAL_DEMO_SHORT_PASSWORDS=0`、`ENABLE_DEMO_IDENTITY_RECOVERY=false`；生产代码也强制拒绝演示短密码与“实名+学号”重置。本轮仅允许账号登录，不能通过游客入口、旧游客存储值或直接业务请求绕过。账号注册不等于获得队长/信息员/管理员角色。

当前认证使用 `Authorization: Bearer <token>`；会话在数据库保存摘要，有效期为代码固定的 7 天，客户端保存返回的令牌，退出调用注销接口。API 没有设置登录 Cookie，也没有 `COOKIE_DOMAIN`、`JWT_SECRET`、`SESSION_SECRET` 配置。不要凭空添加 Cookie 参数或认为 `SameSite=None` 能修好 Bearer 登录。未来如改用 Cookie，必须同时实现服务端 Cookie、`Secure`/`HttpOnly`、跨站 `SameSite`、客户端凭据模式、精确 Origin + `credentials` 和 CSRF 防护；此文不把它写成现成功能。

S3/微信/Sentry 的根模板变量不代表已集成这些服务。本轮媒体使用本地持久卷；API/Worker 尚未初始化 Sentry SDK，设置 DSN 不会自动产生错误追踪。Worker 当前消费 `match.report` 与 `match.report.notification`，通知 receipt 不等于微信/邮件外部投递。

## 4. Linux 服务器首次部署

以下为 Bash 步骤，假设已获授权的机器预先装好 Git、Docker Engine 与 Compose 插件，仓库位于 `/srv/xiaoqiu/app`。本文不自动安装软件、修改系统网络或获取服务器权限。先选定本轮全部验收通过的提交；不要默认跟随尚未审查的 `main`。

```bash
cd /srv/xiaoqiu/app
git status --short
git rev-parse HEAD
docker version
docker compose version
cp infra/release/.env.example infra/release/.env
chmod 600 infra/release/.env
openssl rand -hex 32
```

在目标机器编辑 `.env`：将生成值填入 `POSTGRES_PASSWORD`，配置实际提交、域名、Origin 和后台 API URL。不要提交 `.env`，不要把完整 `docker compose config` 输出贴到工单，它会展开数据库密码。真实密码不放命令参数或构建参数。Docker ignore 同时排除 `.env`、本地 `private-data/` 和备份，不会把报名表、上传文件和密钥打进镜像。

定义本会话使用的函数，后续示例都在仓库目录执行：

```bash
set -euo pipefail
umask 077
dc() {
  docker compose --env-file /srv/xiaoqiu/app/infra/release/.env \
    -f /srv/xiaoqiu/app/infra/release/compose.yaml "$@"
}
dc config --quiet
dc build migration api worker
dc up -d postgres
dc run --rm migration
```

`config --quiet` 校验配置但不输出展开的秘密；空密码会直接失败。迁移镜像执行实际命令 `pnpm --filter @xiaoqiu/api db:migrate:deploy`。只要迁移失败，就停止本次部署，先排查迁移日志。正式库不得执行 `migrate reset`、`db push` 或手工删除迁移记录。

### 4.1 一次性管理员初始化

空库迁移完成后，用真实组织和专用管理员账号执行仓库的 `db:bootstrap-admin`。这个命令事务创建组织、账号、密码凭据、成员关系、`ORGANIZATION_ADMIN` 角色和初始化审计，不授予全平台管理员，不自动开放私信。已有管理员或冲突用户名会拒绝，不能用它静默覆盖现有账号。

```bash
read -rsp '设置管理员密码（12–128 位，不含空白）: ' BOOTSTRAP_ADMIN_PASSWORD
printf '\n'
export BOOTSTRAP_ADMIN_PASSWORD
dc run --rm -e BOOTSTRAP_ADMIN_PASSWORD migration \
  pnpm --filter @xiaoqiu/api db:bootstrap-admin \
  --organization-code campus-football \
  --organization-name '校园足球赛事' \
  --username league-owner \
  --display-name '赛事管理员'
unset BOOTSTRAP_ADMIN_PASSWORD
```

使用私有密码管理器保存密码。CLI 不打印密码；在看到成功结果前不能认为管理员已经创建。把输出的组织 UUID 写入 `.env` 的 `DEFAULT_ORGANIZATION_ID`。这里不多加 `--`，否则 CLI 会把后续参数视为位置参数。只有忘记密码处理机制完成且验证后才对真实用户承诺自助找回，目前使用经身份审核的运维恢复流程。

模板中的 `DEFAULT_TOURNAMENT_ID` 可先保持空。使用后台建立真实赛季、赛事和队伍，发布后再填赛事 UUID；没有正式赛事时应呈现空状态/明确错误，不能读取演示赛事冒充。

### 4.2 启动和检查

组织 UUID 写入后才构建后台（它是构建变量）：

```bash
dc build admin-web
dc up -d api worker admin-web
dc ps -a
dc logs --tail 100 migration api worker
curl --fail --show-error http://127.0.0.1:3101/api/health/live
curl --fail --show-error http://127.0.0.1:3101/api/health/ready
curl --fail --show-error http://127.0.0.1:5180/healthz
```

迁移可重复执行；启动依赖可能再次运行 `migrate deploy`，不会重新 Seed。API `live` 只证明进程响应，`ready` 会查询 PostgreSQL；二者不证明赛事、角色或 Worker 已验收。Worker 是独立常驻进程，没有 HTTP 健康端点，必须同时查日志和实际任务消费。Compose 的 `restart: unless-stopped` / API、Worker 的 `init`、45 秒停止宽限保证正常退出与进程重启；**unhealthy 本身不会触发 Docker 自动重启**，仍需外部监控/运维介入。

容器方案不再额外启动宿主机 `pnpm dev:worker` 或 systemd 的第二套同库 Worker；已有用户手动 Worker 不在本轮停止/替换范围。选定实际部署实例时需明确哪个 Worker 服务同一个数据库。

## 5. HTTPS、反向代理与跨域

若已有 Coolify/Nginx/其他 HTTPS 网关，复用现有管理方式，把 API 指向本机 `127.0.0.1:3101`、后台指向 `127.0.0.1:5180`；同 Docker 网络可指向 `api:3000`、`admin-web:80`。原样保留 `/api` 路径与 Authorization，转发 `Host`、`X-Forwarded-Proto`、`X-Forwarded-For`。不要公开 Docker socket 或 PostgreSQL 端口。不要在反代再加第二套任意 `Access-Control-Allow-Origin`；由 API 的精确 CORS 配置负责。

如果还没有网关，本仓库提供 [Caddyfile](../../infra/release/Caddyfile)：

1. 用户先在授权服务器/域名管理处确认 A/AAAA 指向正确地址、80/443 可达且未被其他网关占用。
2. `.env` 填真实 `API_DOMAIN`、`ADMIN_DOMAIN`、`ACME_EMAIL`。
3. 在这些前提满足后执行以下命令，不在当前 Windows 开发机照搬启动公网网关。

```bash
dc --profile edge run --rm --no-deps edge \
  caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
dc --profile edge up -d edge
dc logs --tail 100 edge
curl --fail --show-error https://api.example.edu/api/health/ready
curl --fail --show-error https://admin.example.edu/healthz
```

Caddy 可自动申请/续签证书，但依赖正确 DNS、可达端口和持久化数据目录；详见[官方 HTTPS 前提](https://caddyserver.com/docs/automatic-https)。本配置用持久卷保存证书状态，并允许 30 MB 请求体（API JSON 上限 26 MB，照片 Base64 会膨胀）。已有 Nginx 反代需相应设置 `client_max_body_size 30m`，否则上传可能返回 413。

API 当前没有显式设置 Express `trust proxy`。反代传真实 IP 并不保证登录风控看到真实访客 IP；共享网关 IP 可能使登录频率统计集中。若需要真实 IP，先由维护者实现仅信任已知反代的配置并测试，不能在公网请求中盲目信任任意 `X-Forwarded-For`。这一点不阻止 Bearer 鉴权，但应在登录压力验收中检查。

跨域预检示例（用实际 API 域名替换）：

```bash
curl --include --request OPTIONS https://api.example.edu/api/auth/login \
  --header 'Origin: https://xiaoqiu-h5-trial.gb-physics.chatgpt.site' \
  --header 'Access-Control-Request-Method: POST' \
  --header 'Access-Control-Request-Headers: content-type,x-organization-id'
```

允许来源应返回与请求相同的 `Access-Control-Allow-Origin`；未知来源不能获得许可。CORS 是浏览器限制，不能代替账号和组织权限。验收仍要通过匿名请求、错误组织和越权角色检查服务端拒绝。

## 6. 接通现有 Sites H5

当前 `https://xiaoqiu-h5-trial.gb-physics.chatgpt.site` 是公开、刻意禁用 API 的纯前端预览。这份后端部署不会自动解除该预览限制，也没有在本轮发布 Sites。

后端 HTTPS 与组织就绪后，需要后续重新构建并发布连接真实 API 的 H5：

```bash
TARO_APP_API_BASE_URL=https://api.example.edu \
TARO_APP_ORGANIZATION_ID=实际组织UUID \
TARO_APP_LOCAL_SHORT_PASSWORDS=0 \
  pnpm --filter @xiaoqiu/mini-program build:h5
```

H5 的 base URL **不带 `/api`**，Repository 会补前缀；后台 `VITE_API_BASE_URL` 则带 `/api`。两个都是构建时变量，单改服务器 `.env` 不会改已发布的 JS。发布前还需去掉那次 Sites 预览专门使用的禁 API 设置/占位地址；不能把真实失败改成 Mock 成功。若 Sites 发布域名变化，API `CORS_ORIGINS` 同步加入新 Origin，并重建/更新 API 容器配置。

管理员组织 UUID、API URL 属于公开路由配置，可以注入 H5；数据库密码与管理员密码不得放入 `TARO_APP_*` 或 `VITE_*`。需要公开媒体 URL 时，客户端会按 API 域名解析 `/api/media/...`，不应让图片地址指回本机。

联调时先在浏览器 Network 核实请求目标为 HTTPS 后端，确认退出/会话失效回登录，API 断开时显示错误与重试；然后按第 11 节验收桌面/手机。公网前端能打开、API `ready` 成功，分别都不是联调完成证据。

## 7. 数据库迁移、演示 Seed 与正式录入

`db:migrate:deploy` 适用于新的或已有的目标实例，迁移只增量执行。不能将本机日常库、用户正在使用的库或真实赛事库拿来跑集成测试。测试使用独立库和测试账号，至少执行：全新迁移 → Seed 一次 → Seed 再次 → 回归测试；记录实际 16 支参赛队、每队锁定名单、4 组各 4 队以及 8 队淘汰赛集合，不把 8 队淘汰赛误解释成仅 8 队报名。

演示命令仅用于明确隔离、无真实用户资料的开发/验收数据库：

```bash
# 仅在已经单独配置/核实 DATABASE_URL 的隔离测试库中执行。
pnpm --filter @xiaoqiu/api db:migrate:deploy
pnpm --filter @xiaoqiu/api db:seed
pnpm --filter @xiaoqiu/api db:seed
```

Seed 写入 `DEMO_FIXTURE`、虚构球队球员、固定演示账号，并输出公共演示密码；它不是正式组织初始化命令，也不是修复真实赛事的通用脚本。不得在正式库“先 Seed 再改名”；安全 bootstrap 不创建演示赛事。正式球队、球员、报名、赛程、角色和事件由授权后台/业务接口创建，保留名单版本、审计、权限和幂等规则。

空正式组织没有球队、名单和赛事是正常初始化状态。发布真实赛事前完成队伍、球员、报名及锁定名单；在设置默认赛事之后验证首页、搜索、球队详情、名单、赛程、积分与淘汰树均读取同一组织/赛事。

## 8. 媒体持久化

API 运行时文件位置核对如下：

| 内容              | 容器内实际位置                    | 保存方式                                                       |
| ----------------- | --------------------------------- | -------------------------------------------------------------- |
| 用户/球员上传头像 | `/app/private-data/media/avatars` | 代码以编译后 `dist/media` 相对路径解析；本轮无头像目录环境变量 |
| 动态照片          | `/app/private-data/media/posts`   | 显式传 `POST_MEDIA_DIRECTORY`                                  |
| 演示队徽/人物图片 | `/app/apps/api/demo-media`        | 镜像内静态演示资源，不当作上传文件                             |

release 与 Coolify 都将持久卷挂在 `/app/private-data/media`，包含头像、帖子子目录；更换 API 镜像不应丢失上传文件。数据卷不等于备份。当前本地媒体适配器适合单实例；多 API 实例必须共享已验证的文件系统，或另行实现对象存储，不能只填 `S3_*` 就认为已支持。

验收：上传头像/动态照片 → 记录公开媒体路径 → 重建 API 容器 → 刷新同一资料/动态 → 图片仍可读取。恢复数据库时还要恢复同一时间点媒体，否则 URL 存在而文件 404。

## 9. 备份与恢复演练

以下 Bash 命令会产生包含个人资料的备份，在授权服务器由运维执行，保存在仓库以外，使用受限权限与加密异地副本。建议每日备份，赛事日提高频率；保留周期按用户数据政策设定。恢复演练成功之前，不能把“有 dump 文件”当作可恢复。

### 9.1 一致备份

首次或更新前做短维护窗口，暂停业务写入与 Worker，保证数据库和媒体同一时间段；不要在业务运行中单独复制 PostgreSQL 数据目录。

```bash
project_name=xiaoqiu-release  # 必须与该实例 .env 一致
backup_dir="/srv/xiaoqiu-backups/$(date -u +%Y%m%dT%H%M%SZ)"
install -d -m 700 "$backup_dir"
dc stop edge api worker admin-web
dc exec -T postgres sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "$backup_dir/database.dump"
dc run --rm --no-deps --entrypoint sh \
  -v "$backup_dir:/backup" \
  -v "${project_name}_media_data:/media:ro" migration \
  -c 'tar -C /media -czf /backup/media.tar.gz .'
git rev-parse HEAD > "$backup_dir/git-commit.txt"
dc exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "SELECT migration_name FROM _prisma_migrations WHERE finished_at IS NOT NULL ORDER BY started_at"' \
  > "$backup_dir/migrations.txt"
sha256sum "$backup_dir/database.dump" "$backup_dir/media.tar.gz" \
  > "$backup_dir/checksums.txt"
dc up -d api worker admin-web
# 实际使用 edge 的实例才执行：
dc --profile edge up -d edge
```

逐条检查命令退出码，失败就停止，不能继续把不完整文件标为成功。把 `.env` 与镜像 digest 的备份放在另一份加密的运维记录，不能提交 Git。PostgreSQL custom dump 用 `pg_restore` 恢复，不通过文本替换密码；机制见[PostgreSQL 官方 dump 文档](https://www.postgresql.org/docs/17/backup-dump.html)。

这些重定向针对 Bash。Windows PowerShell 不应照搬二进制 `pg_dump > 文件`；改为在容器内写 `/tmp/database.dump` 后用 `docker cp` 导出，并核验 SHA-256。正式备份不从开发电脑远程读取真实库。

### 9.2 恢复到独立实例

先准备 `infra/release/.env.restore`（该文件名被 Git/Docker 忽略）：复制模板后填新的随机密码、`COMPOSE_PROJECT_NAME=xiaoqiu-restore`、`POSTGRES_DB=xiaoqiu_restore`、与备份对应的 `APP_VERSION`、`API_BIND_PORT=3102`、`ADMIN_BIND_PORT=5181`。使用备份内真实组织 UUID；不启动 `edge`，不覆盖原实例卷。

```bash
dcr() {
  docker compose --env-file /srv/xiaoqiu/app/infra/release/.env.restore \
    -f /srv/xiaoqiu/app/infra/release/compose.yaml "$@"
}
restore_project=xiaoqiu-restore
# backup_dir 指向第 9.1 节已核验的备份目录
sha256sum --check "$backup_dir/checksums.txt"
dcr config --quiet
dcr up -d --wait postgres
dcr exec -T postgres sh -c \
  'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner --no-acl --exit-on-error' \
  < "$backup_dir/database.dump"
dcr run --rm --no-deps --entrypoint sh \
  -v "$backup_dir:/backup:ro" \
  -v "${restore_project}_media_data:/media" migration \
  -c 'tar -C /media -xzf /backup/media.tar.gz'
dcr run --rm migration
dcr up -d --no-deps api worker admin-web
curl --fail --show-error http://127.0.0.1:3102/api/health/ready
```

用备份对应的源码/镜像启动；将新迁移应用到备份库前，先在独立恢复实例验证。检查账号登录、组织/赛事数量、球队球员、报告版本、媒体和 Outbox 消费，记录恢复时间与恢复点。恢复不运行 bootstrap 或 Seed。确认恢复可用后再由负责人决定真实切换；此文不默认删除旧卷，不使用 `docker compose down -v`。

## 10. 健康、日志、更新与回滚

```bash
dc ps -a
dc logs --tail 200 api worker migration
dc exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT topic, status, count(*) AS jobs, min(available_at) AS oldest_available_at
FROM outbox_jobs
WHERE topic IN ('match.report', 'match.report.notification')
GROUP BY topic, status ORDER BY topic, status;
SELECT id, topic, status, attempt_count, max_attempts, last_error_code,
       available_at, locked_until, correlation_id
FROM outbox_jobs
WHERE topic IN ('match.report', 'match.report.notification')
  AND status IN ('FAILED_RETRYABLE', 'FAILED_PERMANENT')
ORDER BY available_at LIMIT 20;
SQL
```

这里查询实际表/字段，不输出 payload/个人资料。确认报告后应出现并消费相应任务；仅容器 `Up` 无法证明 Worker 正在处理。失败时核对迁移、数据库连通、版本与错误代码；不要改 Outbox payload、伪造 `SUCCEEDED` 或把尚不存在的管理重放 API 当作修复方式。API 请求日志提供方法、脱敏路径、状态、耗时和 request ID；Docker 日志有容量上限，长期监控/日志归档需要用户选定管理平台。

更新顺序：

1. 保存当前 commit、`APP_VERSION`、镜像 digest 和持久化配置；完成第 9 节备份。
2. 在独立验收库对目标 commit 做全新迁移、两次 Seed、回归与 H5 构建；CI 成功后再部署。
3. 工作目录无其他未提交修改后，切换到具体审查提交；更新 `.env` 的 `APP_VERSION`，构建目标镜像，保留旧标签。
4. 维护窗口停止 API/Worker/后台/edge → `dc run --rm migration` → 成功才更新服务。
5. `dc up -d --no-deps --force-recreate api worker admin-web`；验收健康/角色/写入/媒体后再启动原有网关或 edge，并安排对应 H5 发布。

应用回滚仅在旧代码与已升级 schema 兼容时使用。例如旧镜像标签仍存在，在当前 Bash 会话显式覆盖 `APP_VERSION` 再重建容器：

```bash
export APP_VERSION=已记录的旧提交
dc up -d --no-build --no-deps --force-recreate api worker admin-web
unset APP_VERSION
```

不要调用迁移 job 试图“降级”；Prisma `migrate deploy` 不自动回滚 schema。若迁移不向后兼容，保持维护状态，恢复到备份的独立数据库/媒体实例并验证再切换；恢复会丢失备份点后的写入，须由负责人明确接受。若回滚被保留，将 `.env` 的版本同步为实际版本，避免下一次操作误升回去。前端构建变量/接口契约变化时，H5 与后台也要回到对应版本。

## 12. 常见故障与已有 Coolify

| 现象                        | 排查/处理                                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------------------- |
| API ready 503               | 数据库健康、密码一致性、迁移退出码、数据库连接；修改 `POSTGRES_PASSWORD` 不会自动改已有卷里的角色密码 |
| 新 API 未启动               | 看 migration 日志；修复迁移问题后再启动，不绕过失败迁移                                               |
| 浏览器 CORS/Failed to fetch | HTTPS DNS/证书、实际 Origin 白名单、请求是否落到禁 API 预览；curl 正常不能证明浏览器跨域正常          |
| 所有数据为空或组织不可用    | 检查真实组织 UUID、成员关系、发布赛事与默认赛事 UUID；不要用 demo ID 填补                             |
| 后台调用本机地址            | `VITE_API_BASE_URL` 未在构建前配置；重建后台镜像并刷新缓存                                            |
| H5 仍访问占位/127.0.0.1     | 重建并发布 Sites H5，确认 `TARO_APP_API_BASE_URL`；不能只改 API 环境变量                              |
| 图片 404/重启丢失           | 看媒体卷实际挂载与 posts 环境目录；同时恢复数据库/媒体，不只恢复一项                                  |
| 上传 413                    | 反代 30 MB 限制与 API 26 MB JSON 限制；客户端单照片压缩限制仍由业务验证执行                           |
| Worker Up 但无统计更新      | 实际 topic/version/状态与日志；旧 topic 不等于当前消费范围；不直接改任务状态                          |
| bootstrap 拒绝              | 先看组织管理员/用户名是否已存在；不是覆盖管理员工具；通过受审查恢复流程处理                           |
| 公共演示密码可登录          | 实例错误地执行过 Seed；不作为正式上线，先在隔离恢复方案中审查演示账号与数据清理                       |

已有 Coolify 可继续使用 [infra/coolify/compose.yaml](../../infra/coolify/compose.yaml)：它采用外部 PostgreSQL `DATABASE_URL`，不附带数据库。设置精确 `CORS_ORIGINS`、组织/赛事 UUID、后台构建 URL；API 持久卷也已补齐。Coolify 的域名、HTTPS、数据库备份与权限管理由用户现有平台配置，不能同时启动本文件 `edge` 抢占 80/443。安全 bootstrap 用 migration 镜像的一次性任务执行相同 CLI，不运行演示 Seed。
