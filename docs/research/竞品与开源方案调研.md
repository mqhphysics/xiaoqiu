# 晓球：竞品与开源方案调研

> 文档版本：V0.1  
> 调研日期：2026-06-08  
> 文档性质：独立调研材料，暂不直接修改《核心架构.md》。

## 一、调研目的

本次调研主要回答四个问题：

1. 国内外校园、业余足球和综合赛事平台通常如何设计产品？
2. 晓球当前方案还缺少哪些经过真实赛事验证的重要能力？
3. GitHub 上有哪些代码或组件值得直接评估？
4. 哪些项目只能参考思路，不能直接复制或作为项目底座？

筛选时主要考虑：

- 与校园赛事、业余足球、杯赛管理的相关程度。
- 是否有真实产品、公开文档或可运行演示。
- GitHub 项目的维护状态、版本发布、文档、测试和社区规模。
- 开源许可证是否允许在晓球中使用和修改。
- 是否适合微信小程序、Web 管理端和模块化单体架构。

## 二、结论摘要

### 1. 没有一个现成项目可以完整替代晓球

晓球同时包含：

- 校园身份与球员认领。
- 小组赛、淘汰赛和数据榜单。
- 多人协作录入与数据质疑。
- 校园动态社区。
- 微信小程序入口。

现有产品通常只擅长其中一部分。最合理的路线不是套用一个完整系统，而是：

- 借鉴成熟产品的业务流程。
- 采用许可证宽松、边界清楚的开源组件。
- 保留晓球自己的账号、数据、纠错和社区核心。

### 2. 最值得学习的四类样本

- **IMLeagues：** 校园赛事治理、资格管理、申诉、裁判、场地和荣誉体系。
- **Tournify / Bracket：** 多阶段赛事、比分提交、赛程编排和公开赛事页面。
- **Spond / LeagueApps / TeamSnap：** 球队日常管理、名单锁定、签到和赛程变更通知。
- **TapIn / LigaHub / Sofascore / FotMob：** 球员档案、数据荣誉、关注和社区参与。

### 3. 优先值得试验的开源组件

- `brackets-manager.js`：淘汰赛和多阶段赛事逻辑。
- `brackets-viewer.js`：Web 端淘汰赛图展示。
- `react-admin`：快速建设管理后台。
- `FullCalendar`：后台赛程日历和拖拽排期。
- `Apache ECharts`：积分、走势和球员数据可视化。
- `TDesign MiniProgram`：小程序组件与设计规范。
- `Casbin`：复杂作用域权限增长后再考虑接入。
- `BullMQ`：通知、重算和图片处理任务增长后再考虑接入。

### 4. 当前最值得补充的业务能力

按价值排序：

1. 参赛资格、名单提交、名单锁定和历史名单快照。
2. 裁判/现场负责人角色与简化比分提交。
3. 赛程发布版本、场地冲突检查和变更通知。
4. 比赛报告的“草稿、提交、确认、修正”生命周期。
5. 球员出场、签到和淘汰赛资格。
6. 生涯数据、奖杯、赛季荣誉和可分享个人卡片。
7. 数据完整度工作台和批量导入导出。

## 三、重点竞品与可借鉴思路

### 1. IMLeagues：最接近校园场景的参考对象

链接：

- [IMLeagues 平台介绍](https://www.imleagues.com/School/Home.aspx?Control=Privacy&SchID=xMB4MdSTbkJoeX07cPjNaA%3D%3D)

公开介绍显示，IMLeagues 服务大量高校，覆盖：

- 联赛和赛程管理。
- 球员与统计数据。
- 裁判和场地安排。
- 群发通知。
- 争议处理。
- 资格、免责声明和报名。
- 个人长期数据、奖杯与成就。

#### 对晓球最有价值的启示

#### 赛事系统不只是比分系统

真实校园赛事还会遇到：

- 谁具备参赛资格。
- 谁在截止日期前进入正式名单。
- 某球员是否代表多支球队。
- 某球员是否满足淘汰赛出场资格。
- 红牌停赛是否已经执行。
- 裁判、比赛监督和场地是否冲突。

晓球当前架构的数据展示很强，但赛事治理仍可以补充。

#### 荣誉体系很适合校园足球

IMLeagues 将普通参与者变成拥有长期记录的“个人运动员”，提供终身统计、奖杯和成就。这与晓球“提升普通球员荣誉感”的定位高度一致。

建议后续增加：

- 赛季冠军、最佳射手、最佳门将等奖杯。
- 参赛次数、出场次数、进球里程碑。
- 球员个人荣誉墙。
- 球队历年成绩。
- 可分享的赛季总结卡片。

这些内容比复杂的“球员算法评分”更适合早期校园数据条件。

#### 体育道德评分可以保留为后期能力

部分使用 IMLeagues 的高校会由裁判在赛后对球队的体育道德表现评分，并将其用于淘汰赛资格。晓球可以保留：

```text
SportsmanshipRating(
  match_id,
  team_id,
  score,
  submitted_by,
  reason
)
```

首发阶段不必上线，更不应开放大众投票。未来若赛事方有明确规则，可由裁判或管理员填写。

### 2. Tournify：比分提交和阶段推进值得重点学习

链接：

- [Tournify 产品主页](https://tournifyapp.com/en)
- [比分录入能力](https://tournifyapp.com/features/scorekeeping)
- [裁判录入比分说明](https://help.tournifyapp.com/en/articles/8925192-let-referees-enter-scores)
- [入门与赛事工作流](https://help.tournifyapp.com/en/articles/15069302-getting-started-with-tournify)

Tournify 支持：

- 球队、球员和裁判管理。
- 小组、联赛和淘汰阶段。
- 实时比分与积分。
- 裁判或球队通过专属链接提交比分。
- 管理员复核和覆盖。
- 阶段结束后限制继续提交旧阶段数据。
- PDF、Excel 和打印导出。

#### 对晓球最有价值的启示

#### 将“现场快速提交”与“完整数据编辑”分开

可增加两种录入入口：

- **快速比赛报告：** 裁判或现场负责人只提交比分、比赛结束状态和必要备注。
- **完整数据报告：** 信息员继续补充进球、助攻、红黄牌和时间线。

这样比要求同一个人一次性填完整更符合真实比赛现场。

#### 比赛报告需要生命周期

建议研究以下状态：

```text
DRAFT          草稿
SUBMITTED      已提交，提交者不能直接改
CONFIRMED      管理员或指定角色确认
DISPUTED       某个字段存在质疑
CORRECTED      已修正
```

这与现有比赛状态不是一回事：

- 比赛状态描述比赛进行到哪里。
- 报告状态描述数据是否已经提交和确认。

两者应分开保存。

#### 阶段推进必须显式操作

不建议每次比分变化都立即不可逆地修改下轮对阵。更可靠的流程是：

1. 小组赛或本轮比赛全部达到可确认状态。
2. 系统计算晋级建议。
3. 管理员预览晋级名单和冲突。
4. 点击“确认进入下一阶段”。
5. 系统生成或填充下一阶段对阵。

这样可以防止一场比分修正导致已经发布的淘汰赛结构被后台静默改变。

### 3. LeagueApps：名单、可见性和赛程发布

链接：

- [名单设置、提交截止与锁定](https://support.leagueapps.com/hc/en-us/articles/360039380154-Roster-Settings)
- [赛程日历与变更通知](https://support.leagueapps.com/hc/en-us/articles/23315644300183-New-Club-Scheduling-Experience)
- [移动端赛程、签到和沟通](https://join.leagueapps.com/apps)

#### 对晓球最有价值的启示

#### 名单不是永久可编辑的普通关联表

成熟平台通常支持：

- 名单提交截止时间。
- 队长正式提交名单。
- 提交后锁定。
- 管理员退回或重新开放。
- 区分“草稿名单”和“正式名单”。
- 控制名单字段的公开范围。

建议晓球未来增加：

```text
RosterSubmission(
  tournament_id,
  team_id,
  status,
  deadline_at,
  submitted_at,
  locked_at,
  version
)
```

正式确认时还应生成名单快照，避免球员后来转队后改变历史比赛记录。

#### 赛程需要发布状态与版本

管理员内部排期不应立即对外可见：

```text
DRAFT → PUBLISHED → UPDATED → CANCELLED
```

赛程发布时间、版本号和变化内容都应保存。已发布比赛的时间、地点或对手发生改变时，系统向相关球队和关注者发送聚合通知。

#### 名单字段应按角色控制可见性

例如：

- 姓名、号码和位置可公开。
- 学号只允许管理员查看。
- 联系方式只允许队长和管理员查看。

不能只做“整张名单公开或隐藏”。

### 4. Spond：签到、出勤和提醒

链接：

- [Spond 产品主页](https://www.spond.com/en-us/)
- [球队功能概览](https://www.spond.com/en-us/features-for-teams-overview/)
- [签到与出勤流程](https://www.spond.com/en-us/news-and-blog/attendance-tracking-on-spond/)

Spond 将活动、邀请、报名响应、提醒和实际签到连接在同一流程。

#### 对晓球的启示

校园球队可能需要在比赛前知道：

- 谁能参加。
- 谁不能参加。
- 谁尚未回复。
- 实际到场的是谁。

这可以后续形成：

```text
MatchAvailability
MatchCheckIn
LineupSubmission
```

实际出场名单还可以解决：

- 统计球员出场次数。
- 判断淘汰赛参赛资格。
- 减少进球者选择列表中的无关人员。
- 形成更可信的个人生涯数据。

该能力有价值，但不应阻塞第一版比分和赛程上线。

### 5. TeamSnap：把赛事信息和沟通放在一起

链接：

- [TeamSnap 产品主页](https://www.teamsnap.com/)
- [TeamSnap ONE](https://www.teamsnap.com/one)

其主要思路是将报名、名单、赛程、提醒和球队沟通放进一个连续体验。

#### 对晓球的启示

- 比赛详情页不仅展示比分，还应展示时间、地点、变更记录和相关公告。
- 队长不应依赖另一个群反复通知赛程变化。
- 通知点击后应直接进入对应比赛、球队或工单，而不是只有一段无上下文文字。
- 用户关注球队后，可以只接收与该队有关的赛程变化和比赛结果。

晓球暂时不需要重新制造完整即时聊天系统，微信群已经能完成聊天。站内消息更适合承担“结构化且可追踪”的通知。

### 6. TapIn 与 LigaHub：赛事数据和社区应互相导流

链接：

- [TapIn](https://tapinsports.com/)
- [LigaHub](https://ligahub.app/)

两者都强调：

- 业余足球赛事。
- 球队和球员档案。
- 赛程、积分和个人统计。
- 公开页面。
- 社区或球迷参与。
- 分级管理权限。

#### 对晓球的启示

晓球不应把“数据”和“社区”做成完全隔离的两个产品。

可以建立以下连接：

- 比赛结束后自动生成可编辑的赛果动态。
- 球员进球事件可以跳转到球员档案。
- 球员档案可以聚合与本人有关的官方比赛和社区内容。
- 球队页可以展示赛程、历史成绩和球队动态。
- 动态可以关联比赛、球队或球员，而不只是普通文本。
- 首页推荐优先使用结构化赛事关系，而不是一开始就做复杂推荐算法。

建议 `Post` 支持可选关联：

```text
related_match_id
related_team_id
related_player_id
```

### 7. Sofascore 与 FotMob：数据应转化为荣誉和故事

链接：

- [Sofascore 球员数据展示思路](https://www.sofascore.com/news/sofascores-attribute-overview-the-ultimate-tool-for-player-analysis/)
- [Sofascore 阵容展示](https://www.sofascore.com/news/sofascores-redesigned-lineup-feature-take-match-analysis-to-the-next-level/)
- [FotMob 比赛覆盖与球员评分案例](https://www.fotmob.com/sw/topnews/27924-fotmob-joins-soccer-aid-unicef-official-live-score-partner)

#### 值得学习

- 比赛时间线比普通事件表格更容易阅读。
- 球员档案应区分单场、赛季和生涯数据。
- 数据使用颜色、徽章和卡片表达，普通用户更容易理解。
- 关注球队或球员后获得针对性通知。
- 历史数据可以产生“里程碑”和“赛季最佳”等内容。

#### 暂时不要照搬

校园比赛很难稳定采集传球、射门位置、抢断和跑动数据，因此首发阶段不适合做：

- 复杂球员评分。
- 热力图。
- 预期进球。
- 复杂技术属性雷达图。

早期可以可靠实现：

- 出场、进球、助攻、红黄牌和零封。
- 最佳射手、助攻王、最佳门将。
- 连续进球、百场等里程碑。
- 管理员或赛事方评选的单场最佳。

## 四、GitHub 开源项目筛选

### A 级：值得直接拉取、运行和评估

#### 1. brackets-manager.js

- 仓库：[Drarig29/brackets-manager.js](https://github.com/Drarig29/brackets-manager.js/)
- 许可证：MIT。
- 调研时状态：持续发布版本，2026 年 5 月仍有新版本。
- 支持：循环赛、单败淘汰、双败淘汰、轮空、弃权、多阶段、比赛状态和存储适配。

适合晓球的用途：

- 验证淘汰赛结构和晋级算法。
- 参考多阶段赛事的数据模型。
- 作为独立“对阵计算模块”使用。

使用原则：

- 不让第三方库直接控制晓球全部赛事数据库。
- 在外部增加适配层，将晓球的 `Tournament/Stage/Round/Match` 转换成库模型。
- 比分、审计、质疑和球员事件仍由晓球自己管理。
- 必须补充足球规则测试，包括弃权、点球大战、三四名决赛和比分回改。

初步结论：**优先做技术验证，具有真实采用价值。**

#### 2. brackets-viewer.js

- 仓库：[Drarig29/brackets-viewer.js](https://github.com/Drarig29/brackets-viewer.js/)
- 许可证：MIT。
- 支持：循环赛、单败、双败展示，主题、翻译、队徽、比赛点击和自定义轮次名称。

适合晓球的用途：

- Web 管理端或未来 H5 的淘汰赛图。
- 快速验证对阵数据结构。
- 参考移动端横向滚动和比赛节点布局。

限制：

- 它依赖浏览器 DOM，不能假设可直接放入原生微信小程序。
- 小程序端可能需要根据相同数据模型自行实现 `scroll-view`、Canvas 或组件布局。

初步结论：**Web 端可直接评估，小程序端主要借鉴数据格式和交互。**

#### 3. react-admin

- 仓库：[marmelab/react-admin](https://github.com/marmelab/react-admin)
- 许可证：MIT。
- 定位：基于 REST/GraphQL API 快速构建后台 CRUD 和业务管理界面。

适合晓球的用途：

- 白名单导入与查询。
- 球队、球员、赛事和赛程管理。
- 账号申诉、质疑工单和审计记录。
- 数据筛选、分页和批量操作。

需要自行开发：

- 淘汰赛编辑器。
- 比赛版本对比。
- 复杂权限界面。
- 赛程拖拽排期。

初步结论：**很适合减少管理后台基础页面的重复开发。**

#### 4. FullCalendar

- 仓库：[fullcalendar/fullcalendar](https://github.com/fullcalendar/fullcalendar)
- 标准版许可证：MIT。
- 定位：Web 端日历、赛程展示与拖拽。

适合晓球的用途：

- 管理员按日、周查看赛程。
- 拖动调整比赛时间。
- 标记场地、赛事、比赛状态。
- 在发布前检查同一球队的时间冲突。

注意：

- 资源时间线等部分高级能力可能属于 Premium，采用前必须核对具体插件许可证。
- 拖拽只是操作界面，服务端仍必须进行球队、场地和裁判冲突校验。

初步结论：**标准日历能力值得采用，高级资源排程先不购买或依赖。**

#### 5. Apache ECharts

- 仓库：[apache/echarts](https://github.com/apache/echarts)
- 许可证：Apache-2.0。

适合晓球的用途：

- 球队赛季走势。
- 球员进球分布。
- 数据完整度看板。
- 管理后台运营统计。

小程序使用时需选择可靠的小程序适配方案并控制包体积，普通积分榜仍应使用原生列表，不要所有数据都做成图表。

初步结论：**Web 管理端优先，小程序按需使用。**

#### 6. TDesign MiniProgram

- 仓库：[Tencent/tdesign-miniprogram](https://github.com/Tencent/tdesign-miniprogram)
- 许可证：MIT。
- 调研时状态：2026 年 5 月仍持续发布版本。

适合晓球的用途：

- 列表、卡片、标签、弹窗、表单、上传和导航。
- 统一小程序视觉语言。
- 降低基础组件维护成本。

还可参考：

- [TDesign 小程序零售模板](https://github.com/Tencent/tdesign-miniprogram-starter-retail)

零售模板业务与晓球无关，但其 `components / model / pages / services / utils` 目录组织、请求层和自定义 TabBar 值得参考。

初步结论：**建议作为小程序首选组件库。**

### B 级：可采用，但应在需求增长后引入

#### 1. Casbin

- 仓库：[apache/casbin](https://github.com/apache/casbin)
- 许可证：Apache-2.0。
- 支持：ACL、RBAC、带域/租户的 RBAC、ABAC 和优先级规则。

适合晓球的地方：

```text
某用户
在某赛事/球队/比赛范围内
对某资源
执行某操作
```

例如：

```text
张三是赛事 A 的信息员
李四是球队 B 的队长
王五是比赛 C 的临时现场负责人
```

首发角色少时，数据库 `RoleAssignment` 加服务端代码已经够用。只有权限规则明显复杂、频繁变化时再接入 Casbin，避免过早增加抽象。

#### 2. BullMQ

- 仓库：[taskforcesh/bullmq](https://github.com/taskforcesh/bullmq)
- 许可证：MIT。
- 定位：基于 Redis 的后台任务队列，支持重试、延迟、并发、去重和任务依赖。

适合后期处理：

- 生成聚合通知。
- 图片压缩和审核。
- 重算积分、榜单和晋级关系。
- 发送微信订阅消息。
- 生成赛季总结和分享图片。

首发用户量小时，可以先使用数据库 `OutboxJob` 表和单个后台 Worker。任务量明显上升后再迁移 BullMQ。

### C 级：非常适合研究完整赛事工作流，但谨慎复制

#### 1. Bracket

- 仓库：[evroon/bracket](https://github.com/evroon/bracket)
- 文档：[Bracket Docs](https://docs.bracketapp.nl/)
- 许可证：AGPL-3.0。
- 技术栈：FastAPI、Vite/TypeScript、PostgreSQL、Docker。
- 支持：循环赛、单败、瑞士制、多阶段、多分组、场地拖拽排期、公开看板、球队和球员、CSV 导入。

最值得研究：

- 赛事创建向导。
- 多阶段和多分组数据结构。
- 球队与球员批量导入。
- 场地和时间排程。
- 公开大屏与管理后台分离。
- Docker 部署和项目目录。

许可证提醒：

AGPL 对通过网络提供修改后软件的场景有较强源代码开放要求。除非晓球决定按兼容方式开源并完成许可证评估，否则应：

- 运行演示和阅读代码。
- 学习业务流程和数据建模。
- 不直接复制其代码进入晓球。

初步结论：**最佳完整参考项目之一，不建议在未确认许可证策略前作为代码底座。**

#### 2. Zuluru3

- 仓库：[Zuluru/Zuluru3](https://github.com/Zuluru/Zuluru3)
- 许可证：GPL-3.0。
- 定位：较完整的 Web 体育联赛管理系统。

适合研究：

- 联赛、名单、出勤和定时任务。
- 长期运营中的角色和后台流程。
- 主题和可配置赛事站点。

限制：

- PHP/CakePHP 技术栈可能与晓球最终选择不一致。
- 产品历史较长，界面和部分设计不一定适合移动端。
- GPL 代码复制和分发存在许可证义务。

初步结论：**研究成熟业务边界，不作为首选代码底座。**

### D 级：课程项目和小型项目，只适合局部参考

#### 1. FootballTournamentsAndLeaguesManager

- 仓库：[MikolajP13/FootballTournamentsAndLeaguesManager](https://github.com/MikolajP13/FootballTournamentsAndLeaguesManager)
- 许可证：MIT。
- 功能：联赛、淘汰赛、球队、球员、射手、助攻、红黄牌、比赛报告和事件时间线。

值得看：

- 足球专属数据字段。
- 比赛报告页面。
- 卡牌与进球时间线。
- 小组赛加淘汰赛组合。

不建议：

- 直接作为生产系统底座。
- 未经过独立评审就复用数据库设计。

#### 2. Sports-League-Management-System

- 仓库：[kaimg/Sports-League-Management-System](https://github.com/kaimg/Sports-League-Management-System)
- 许可证：MIT。
- 技术：Flask，带公开数据库脚本。

值得看：

- 基础联赛表结构。
- 简单的球队、比赛、积分和统计流程。

项目没有正式 Release，整体更接近数据库课程项目。可用于对照字段，不应据此判断生产可靠性。

#### 3. tournament-js/roundrobin

- 仓库：[tournament-js/roundrobin](https://github.com/tournament-js/roundrobin)
- 许可证：MIT。
- 作用：使用标准算法生成循环赛轮次。

可以用于：

- 验证基础单循环对阵生成。
- 作为单元测试的结果对照。

不能单独解决：

- 场地和时间约束。
- 同队休息间隔。
- 主客平衡。
- 临时延期。
- 多组和跨组规则。

初步结论：**算法很小，可以参考，但不要把“生成对阵”误认为“完成排赛”。**

## 五、建议加入晓球候选池的产品能力

以下内容先进入“候选池”，暂不直接写入核心架构。

### P0：在数据库定型前应考虑

#### 1. 规则版本

不同年份赛事规则可能改变。建议考虑：

```text
CompetitionRuleVersion
RankingRule
EligibilityRule
SuspensionRule
```

已经开始的赛事绑定确定的规则版本，后续修改规则不能悄悄改变历史结果。

#### 2. 名单提交、锁定和快照

至少需要区分：

- 球队当前成员。
- 某项赛事报名名单。
- 某场比赛实际出场名单。

三者不能用同一张简单关系表替代。

#### 3. 比赛报告与比赛状态分离

建议将：

- 比赛是否开始、结束、取消。
- 数据是否草稿、提交、确认、修正。

拆成两个状态字段或两个对象。

#### 4. 场地和裁判成为正式实体

```text
Venue
Pitch
Official
MatchOfficialAssignment
```

即使首发不做复杂排班，数据库也应避免把场地和裁判永远保存成自由文本。

#### 5. 赛程发布版本

赛程草稿、发布、变更和取消应有记录。这样才能可靠地向相关人员发送“哪里发生了变化”。

### P1：首发后较快增加

#### 1. 数据完整度工作台

管理员看到：

- 哪些比赛只有比分没有事件。
- 哪些事件缺少球员。
- 哪些比赛没有信息员。
- 哪些名单没有提交。
- 哪些质疑长期未处理。

相比被动等待消息，这种“待办总览”更能减少运营工作。

#### 2. 快速比赛报告

现场角色只填写：

- 最终比分。
- 点球比分。
- 是否弃权。
- 红牌数量。
- 简短备注。

之后由信息员补全事件。

#### 3. 批量导入、导出和打印

至少支持：

- Excel/CSV 导入白名单、球队和球员。
- 导出赛程、名单、比赛报告和积分榜。
- 生成适合打印或群内转发的文件。

真实校园赛事中，表格不会消失。好的平台应能吸收和输出表格，而不是强迫管理员手工重录。

#### 4. 关注与定向通知

允许用户关注：

- 球队。
- 球员。
- 赛事。

通知优先覆盖：

- 比赛时间或地点变化。
- 比赛开始和结束。
- 质疑处理结果。
- 球员或球队的新荣誉。

### P2：数据积累后增加

#### 1. 生涯与荣誉体系

- 赛季数据。
- 生涯数据。
- 奖杯和勋章。
- 里程碑。
- 历年球队履历。

#### 2. 自动生成结构化动态

例如：

- 某队晋级四强。
- 某球员完成帽子戏法。
- 射手榜榜首发生变化。
- 决赛对阵正式产生。

系统只生成草稿或结构化卡片，社区内容仍允许用户补充观点和图片。

#### 3. 分享卡片

可生成：

- 比赛结果海报。
- 下一场比赛预告。
- 球员赛季总结。
- 球队晋级路线。
- 射手榜和积分榜。

微信传播环境下，这类图片可能比复杂站内推荐更有效。

## 六、对当前技术路线的具体建议

### 1. 小程序

建议优先组合：

```text
原生微信小程序
+ TypeScript
+ TDesign MiniProgram
+ 自有 API Client
+ 自有状态与缓存封装
```

理由：

- 首发目标明确是微信小程序。
- 原生能力、包体积和问题排查最直接。
- TDesign 维护活跃且许可证宽松。
- 不需要为了尚未开始的 App 提前承担跨端兼容成本。

### 2. Web 管理端

建议优先验证：

```text
React
+ react-admin
+ FullCalendar
+ Apache ECharts
+ 自定义赛事组件
```

基础 CRUD、筛选、表单和工单使用 `react-admin`；赛事日历、版本对比和淘汰赛编辑器单独开发。

### 3. 淘汰赛模块

建议做一个两周以内的技术原型：

1. 使用 `brackets-manager.js` 创建小组赛加单败淘汰。
2. 模拟轮空、弃权、点球和比分修正。
3. 将库数据映射到晓球拟定表结构。
4. 用 `brackets-viewer.js` 在 Web 端展示。
5. 评估小程序端是否自行绘制。

只有测试通过后才决定正式采用。即使采用，也应通过内部 `BracketEngine` 接口隔离第三方库。

### 4. 权限

首发继续使用：

```text
RoleAssignment(user_id, role, scope_type, scope_id)
```

所有权限检查集中在后端授权模块，避免散落在控制器中。角色和作用域增长明显后，再用 Casbin 替换授权判断内部实现。

### 5. 通知与后台任务

首发：

```text
业务事务
→ OutboxJob
→ 单 Worker
→ Notification
```

后期任务量增加后，再将 Worker 层替换为 BullMQ。这样不会为了少量校园用户提前部署 Redis 和复杂队列。

## 七、明确不建议的做法

### 1. 不要直接购买或复制所谓“校园足球毕业设计源码”

常见风险：

- 只有页面截图，没有稳定后端。
- 密码明文或鉴权形同虚设。
- 数据库没有外键、唯一约束和迁移。
- 赛事规则写死。
- 没有并发、审计和版本处理。
- 依赖过期且没有测试。
- 许可证和素材版权不明确。

这类代码可以看页面和字段，但不应成为晓球的基础。

### 2. 不要把完整开源平台硬改成小程序

Bracket、Zuluru 等系统适合研究赛事流程，但：

- 技术栈和交互面向 Web。
- 账号模型与晓球不同。
- 没有晓球的白名单、微信绑定和质疑逻辑。
- 强行修改可能比自己建设模块化核心更慢。
- AGPL/GPL 还带来许可证义务。

### 3. 不要一开始建设即时聊天

球队已有微信群。晓球先做好：

- 结构化通知。
- 赛程变化。
- 业务审批。
- 比赛评论。
- 官方公告。

即时私聊和群聊的审核、举报、未成年人保护、存储和实时连接成本都很高。

### 4. 不要过早上复杂球员评分

数据采集不完整时，复杂评分只会制造争议。先把事实型数据做准，再考虑评价型数据。

### 5. 不要仅凭 GitHub Star 决定采用

采用前至少检查：

- 最近发布和维护时间。
- 是否有明确许可证。
- 是否有测试。
- 是否有正式 Release。
- Issue 是否长期无人处理。
- 是否支持当前运行环境。
- 是否能通过适配层隔离。

## 八、推荐的近期验证任务

这些任务只用于验证，不代表正式进入开发：

1. 本地运行 `evroon/bracket` 演示，记录赛事创建和排程流程。
2. 为 `brackets-manager.js` 编写校园杯赛样例数据和规则测试。
3. 使用 `brackets-viewer.js` 生成一个 16 队淘汰赛 Web 原型。
4. 使用 `react-admin` 制作白名单、球队和质疑工单三个后台原型页。
5. 使用 FullCalendar 验证多场地、同队时间冲突和赛程发布流程。
6. 根据 IMLeagues、Tournify 和 LeagueApps 的流程，画出晓球正式比赛报告状态机。
7. 在决定正式依赖前建立 `THIRD_PARTY_LICENSES.md`，记录组件、版本和许可证。

## 十、最终判断

晓球的方向并不落后于现有产品，反而有两个比较鲜明的特点：

- 校园身份、普通球员档案和长期荣誉结合。
- 信息员协作录入、全民质疑和管理员仲裁结合。

真正需要从成熟平台补上的，不是更多首页功能，而是赛事运营中那些不显眼但决定系统能否长期使用的能力：

- 名单和资格。
- 比赛报告确认。
- 裁判与场地。
- 赛程发布和变更。
- 历史快照。
- 批量导入导出。
- 数据完整度和管理员待办。

代码层面最合理的策略是“自建核心、组件复用、完整项目做参考”。账号、数据可信度、质疑和社区关系应由晓球掌握；淘汰赛算法、后台 CRUD、日历、图表和 UI 组件则没有必要从零发明。
