## 3. 不要混进四条核心分支的事项

### H5 会话功能修复

由用户安排前端功能任务，视觉方案继续由用户调。本轮已查出的具体问题：

- `product.repository.ts`：请求发出后，旧 401 不能清除期间刚换的新 token；旧 `/auth/me` 响应不能覆盖新账号资料。
- `session.ts`：无效 expiresAt 要拒绝；资料/角色更新不能只靠 token 变化触发同步。
- 回归：A 请求延迟→登录 B→A 返回 401/旧身份，B 保留；跨标签退出/换账号、角色撤销后显示更新。

这不是微信任务，不附带微信构建/页面改造。后端已重新查询身份，前端仍需正确应用响应。

### 设置与账号恢复

- 明确哪些通知可关闭、哪些审核通知必须保留，以及这些设置在哪个组织/设备生效。
- 邮箱验证/找回需真实发送服务、一次性令牌、有效期和审计；人工恢复需授权与身份核验，不能只凭姓名/学号。
- 自动续期、设备列表、撤销其它会话需要独立策略与测试，当前固定七天会话不伪装成已支持。
- 涉及 schema/新 API 的设置先交集成负责人形成小契约，再分配实现；不把整个后台规划一次塞入权限分支。

### 运营与部署

通知分页、反馈申诉/重开、赛事范围举报授权、外部推送、无处理人告警、HTTPS/媒体持久化与备份恢复分别排任务。简单站内反馈闭环通过不等于生产运营完整。

## 4. 我怎样验收下一轮成果

1. 每个任务提交哈希、文件列表、API/模型影响、已做/未做、命令与测试库标识，不提交凭据或用户资料。
2. 审查 diff 与公共文件越界情况；测试必须覆盖真实角色、组织/对象隔离、重复与并发请求、审计和通知事务。
3. 完成一个任务后先做定向验收，再由集成负责人纳入集成分支；每纳入一条链路就回归。
4. 最后用独立试运行库走“真实赛事 → 队长提交名单 → 管理员锁定 → 信息员报告 → 管理员确认 → 公开统计/晋级 → 结果修正”整轮。
5. 真数据库、HTTP 往返、浏览器业务、正式部署与微信真机分别记结果，不互相替代。用户未授权时不推送或部署。

后续还需用户提供：比赛日期与赛制、同分/弃权/点球规则、名单人数与资格期限、各工作人员职责、服务器条件。这些决定验收规则，不阻止先按上述边界准备任务。
