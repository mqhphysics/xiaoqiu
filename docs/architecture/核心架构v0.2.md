# 晓球：校园足球杯赛多端数据与社交平台核心架构

> 文档版本：V0.2  
> 更新日期：2026-06-08  
> 当前目标：先完成可投入真实校园杯赛使用的微信小程序和轻量管理后台，并为未来 Web、App 和更多赛事扩展保留稳定的数据基础。

## 一、产品定位与设计原则

### 1. 产品定位

- **产品名称：** 晓球。
- **最终形态：** 微信小程序、Web 端和独立 App 组成的多端平台。
- **首发形态：** 微信小程序为主要用户端，另配一个轻量 Web 管理后台。
- **核心价值：** 长期沉淀校园杯赛、球队和球员数据，通过动态社区、个人档案和榜单增强普通球员的参与感与荣誉感。
- **视觉风格：** 参考成熟体育资讯产品的布局，保持整洁、克制、清晰，避免无意义动效。

### 2. 核心工程原则

- **低门槛优先：** 首发阶段不强制绑定邮箱或进行复杂实名认证，尽量减少注册流失。
- **数据可追溯：** 重要数据允许修正，但不得无痕覆盖或物理删除。
- **服务端可信：** 权限、比分、积分、榜单和晋级结果均由服务端校验或计算，不能只依赖前端。
- **允许逐步完善：** 比赛比分可以先发布，进球和助攻事件可以稍后补录。
- **并发不覆盖：** 多名信息员同时编辑时，后提交者不能静默覆盖先提交者。
- **模块化单体优先：** 首发阶段不拆微服务，但业务模块和数据边界必须清晰，便于后续扩展。

## 二、账号、注册与微信登录

### 1. 学生白名单

系统上线前由管理员导入包含“姓名 + 学号”的学生名单，生成 `StudentIdentity` 记录。

每条白名单记录必须具有唯一学号，并包含以下状态：

- `UNCLAIMED`：尚未注册。
- `CLAIMED`：已被某个账号注册。
- `FROZEN`：身份存在争议，暂时禁止登录和重新注册。

姓名和学号只用于注册比对及管理员核验。普通用户、社区页面和公开接口不得展示完整学号。

### 2. 首次注册流程

用户首次进入小程序时，可以浏览公开内容；需要互动时进入注册流程：

1. 输入姓名和学号。
2. 服务端校验该组合是否存在于白名单。
3. 校验该身份是否仍为 `UNCLAIMED`。
4. 输入密码和昵称。
5. 服务端在同一数据库事务中创建用户、占用白名单身份并绑定当前微信身份。
6. 注册成功后直接进入平台。

首发阶段不强制邮箱、短信或校园统一认证。此方案属于**低门槛身份声明**，不能等同于严格实名认证；系统通过账号申诉、操作审计和权限控制降低冒用造成的影响。

### 3. 昵称与登录

- 昵称既是公开展示名称，也是可选登录凭据。
- 首发阶段要求昵称全平台唯一，比较时忽略大小写并去除首尾空格。
- 用户可使用“学号 + 密码”或“昵称 + 密码”登录。
- 修改昵称后，新的昵称立即成为新的登录名，旧昵称不再可用于登录。
- 学号永远不能公开展示，也不能通过搜索接口反查用户。

若未来用户量增大或允许重名，应将“唯一登录名”和“公开昵称”拆为两个字段；数据库从首发阶段即分别保留 `login_name` 与 `display_name`，首发时两者默认相同。

### 4. 微信自动登录与切换账号

小程序调用微信登录能力取得临时凭证，服务端换取 `openid` 并查询微信绑定关系。

- 一个微信身份首发阶段只绑定一个晓球账号。
- 注册或密码登录成功后，可以绑定当前微信身份。
- 用户只是关闭小程序或长期未打开时，下次可使用同一微信身份自动登录。
- 用户主动点击“退出登录”后，服务端撤销当前会话并暂停该微信绑定的自动登录能力。
- 用户再次进入或切换其他账号时，必须输入学号/昵称和密码。
- 新账号验证成功后，可将当前微信身份改绑到新账号；改绑必须记录审计日志，并使旧账号在该微信上的会话失效。

未来 Web 和 App 端仍使用“学号/登录名 + 密码”登录；各端共享同一用户账号，但会话彼此独立管理。

### 5. 密码与会话安全

- 服务端只保存密码哈希，推荐使用 Argon2id；不得保存、记录或返回明文密码。
- 登录成功后签发短期访问令牌和可撤销的长期会话。
- `User` 中保留 `auth_version`。重置密码、冻结账号或确认账号冒用时递增该版本，使全部旧令牌立即失效。
- 登录、注册和申诉接口必须进行频率限制，防止批量尝试学号、姓名或密码。
- 连续登录失败达到阈值后进行短时限制，不永久锁死账号。
- 日志中的姓名、学号、令牌和密码必须脱敏。

### 6. “我的账号已被注册”申诉

白名单身份已为 `CLAIMED` 时，注册页展示“我的账号已被注册”入口。用户填写联系方式、情况说明和可用于线下核验的材料，生成 `AccountAppeal` 工单。

管理员通过线下或其他可靠方式确认本人后执行账号找回：

1. 将账号暂时冻结。
2. 生成一次性临时密码或一次性重置凭证。
3. 递增 `auth_version`，撤销该账号全部会话。
4. 解除或暂停原微信绑定。
5. 记录处理管理员、依据、时间和操作内容。
6. 本人使用临时凭证登录，立即设置新密码并重新绑定微信。

管理员不能查看用户旧密码。单纯修改数据库中的密码但不撤销会话是不完整的找回操作。

首发阶段不强制邮箱找回；后续可增加邮箱、校园邮箱或其他二次验证方式。

## 三、角色与权限模型

角色不能只做成 `User.role` 单字段，因为同一用户可以同时是球员、队长和信息员，并且权限可能只对某支球队、某项赛事或某场比赛有效。

使用 `RoleAssignment(user_id, role, scope_type, scope_id)` 表达授权范围：

- **游客：** 浏览公开资讯、赛程和数据。
- **普通学生：** 发布动态、点赞、评论、认领球员、申请加入球队、提交质疑。
- **球队队长：** 在指定球队范围内维护资料、审核入队申请和管理名单。
- **认证信息员：** 在指定赛事或比赛范围内录入比分和比赛事件。
- **赛事管理员：** 处理指定赛事的质疑、赛程、名单和数据修正。
- **超级管理员：** 管理全平台账号、权限、公告和审计。

所有敏感接口都必须在服务端校验角色及作用范围。前端隐藏按钮只用于界面展示，不能作为权限保护。

## 四、赛事与比赛数据模型

### 1. 赛事层级

采用以下层级，避免赛季、赛事、小组和淘汰轮次混在一起：

```text
Season
└── Tournament
    ├── Stage（小组赛/淘汰赛）
    ├── Group
    ├── Round
    └── Match
```

球队参赛和球员名单通过 `TeamRegistration`、`RosterEntry` 按赛事保存，不能直接假设球队当前成员就是某一历史赛季的参赛名单。

### 2. 比分与事件是两层数据

`Match` 保存官方比分，`MatchEvent` 保存进球、助攻、红黄牌等明细。

- **比分是比赛结果的主要来源。** 积分榜、淘汰赛晋级和比赛卡片以 `Match` 中的官方比分为准。
- **事件是可逐步补全的明细。** 比分为 3:1 时，即使暂时只录入两个进球事件，比赛结果仍然可以发布。
- 系统根据比分和有效进球事件计算 `missing_event_count`，并将事件完整度标记为：
  - `EMPTY`：尚未录入事件。
  - `PARTIAL`：已录入但不完整。
  - `COMPLETE`：事件与比分匹配。
  - `REVIEW_REQUIRED`：事件与比分存在无法自动解释的冲突。
- 事件不完整时，在详情页显示“进球明细待补充”，并向有权限的信息员和管理员生成聚合提醒。
- 点球大战比分、乌龙球、官方判罚比分和弃权必须单独建模，不能简单按普通进球事件相加。
- 信息员离开页面前，客户端应提示仍有未补全事件，但不得强制阻止保存比分或离开。

### 3. 比赛状态

```text
SCHEDULED       未开始
LIVE            进行中
FINISHED        已结束，比分已录入
CONFIRMED       结果已确认
CORRECTED       确认后发生过管理员修正
CANCELLED       已取消
```

质疑不是整场比赛状态。比赛存在质疑时仍正常展示，仅在被质疑的字段或事件旁显示提示。

### 4. 积分与榜单

- 积分榜由服务端根据已生效的比赛结果计算或增量更新。
- 排名规则存入 `RankingRule`，明确胜平负积分及同分比较顺序。
- 射手榜、助攻榜来自有效 `MatchEvent`，因此在明细未补全时必须显示“数据可能不完整”。
- 比分修正后，积分榜、榜单、晋级关系和缓存必须在同一业务事务或可靠任务中重新计算。

### 5. 淘汰赛晋级

不只使用单一 `next_match_id`，而使用：

```text
AdvancementRule(
  source_match_id,
  result_type,       -- WINNER / LOSER
  target_match_id,
  target_slot        -- HOME / AWAY
)
```

这样可以支持胜者晋级、三四名比赛、轮空和主客席位绑定。晋级写入必须幂等；比分被修正时，应重新验证后续对阵，并对已经开赛的下轮比赛发出管理员警告，禁止自动破坏历史数据。

## 五、信息员编辑与并发控制

### 1. 所见即所得编辑

认证信息员在比赛详情页点击编辑图标后，可直接编辑比分和事件。前端体验可以轻量，但服务端仍需经过权限校验、版本校验和事务提交。

- 对尚未填写的比分字段、事件明细或其他空白项，所有具有该场比赛权限的信息员均可直接补录。
- 对已经存在的数据，普通信息员只能查看，不能直接覆盖；如认为数据错误，应提交质疑或修正建议。
- 只有赛事管理员或超级管理员可以在处理工单后替换现有值，且必须填写处理结论。
- 补录新的缺失事件不属于覆盖已有数据，可以继续直接提交。

比赛数据保存后必须生成 `MatchRevision` 和 `AuditLog`，记录：

- 修改人及其权限范围。
- 修改前后的值。
- 修改时间。
- 修改原因或来源。
- 客户端提交时看到的数据版本。

### 2. 空白数据的“先提交者生效”

当某字段为空时，多名信息员可以同时进入编辑：

- 每次读取数据时，客户端获得字段版本或比赛 `version`。
- 提交时使用条件更新或唯一约束保证原子性。
- 第一个成功提交者写入数据并增加版本号。
- 后提交者发现版本已变化时，服务端返回 `409 CONFLICT`，绝不覆盖已有数据。
- 客户端展示“该信息已被其他信息员提交”，同时列出当前值和用户刚才填写的值。
- 后提交者可以放弃、补录仍为空的其他字段，或将差异一键转为质疑。

不能只依赖“请求到达顺序”的前端判断，最终先后顺序必须由数据库事务确定。

### 3. 减少整份录入白费

比赛编辑采用字段级和事件级提交，而不是把整个详情页作为一个不可分割的大对象覆盖：

- 比分更新单独提交。
- 每个进球、助攻或红黄牌事件具有独立 ID。
- 新增事件使用客户端生成的幂等键，重复点击不会产生重复事件。
- 只有发生冲突的字段或事件被拒绝，其他无冲突内容仍可保存。

比分和正式比赛状态属于高风险数据，必须等待服务端确认后显示“保存成功”；点赞等低风险操作可以使用乐观更新。

## 六、质疑、纠错与信誉机制

### 1. 质疑对象

质疑必须指向明确对象，而不是笼统冻结整场比赛：

- 某个比分字段。
- 某条比赛事件。
- 某名进球者或助攻者。
- 某个比赛时间。
- 某个球员、球队或名单字段。

`Dispute` 保存被质疑对象、提交人、理由、建议值、证据、数据版本和处理状态。

### 2. 聚合展示

- 同一用户不能对同一对象重复计数。
- 后台按“目标对象 + 质疑类型”聚合为一个工单，显示独立质疑人数和最新补充说明。
- 管理员收件箱只产生一条聚合消息，人数增加时更新数字，不连续发送大量重复提醒。
- 前台数据保持正常展示，可在旁边标记“有 N 人提出异议”。

### 3. 达到阈值后的处理

系统支持按赛事配置质疑阈值，但首发默认策略为：

- 达到普通阈值：标记为“多人质疑”，提高管理员处理优先级。
- 达到高风险阈值：可以临时隐藏有争议的单条事件或字段展示值，并开放重新补录。
- 原数据始终保留在版本记录中，不能物理删除。
- 比分等会影响积分和晋级的核心数据，默认不得仅凭人数自动清空，必须由管理员确认。
- 自动隐藏策略必须可关闭，且同一批账号、短时间集中提交等异常行为不能简单按人数视为可信。

这样保留“多人质疑后重新录入”的能力，同时避免恶意集中点击直接改变正式赛果。

### 4. 管理员处理

管理员可以：

- 驳回质疑并填写原因。
- 接受质疑并修正数据。
- 将原数据临时隐藏并要求重新录入。
- 恢复历史版本。
- 对恶意质疑者或严重失误的信息员进行警告、扣分、暂停权限或封禁。

信誉分只由已确认的处理结果影响，不因收到质疑自动扣分。每次分数变化都写入 `ReputationLedger`，不得只覆盖一个总分字段。

## 七、消息与收件箱系统

首页右上角放置信封图标，展示未读数量。点击后进入统一收件箱。

消息分为：

- **互动消息：** 点赞、评论、回复。
- **业务消息：** 球员认领、加入球队、队长审核结果、信息员申请结果。
- **数据消息：** 补录提醒、编辑冲突、质疑进展、管理员处理结果。
- **系统消息：** 公告、账号安全、权限变化和版本通知。

核心数据表：

```text
Notification
NotificationRecipient
NotificationAggregation
```

设计要求：

- 通知引用真实业务对象，不复制大量正文。
- 点赞、质疑等高频消息按对象和时间窗口聚合，例如“5 人赞了你的动态”。
- 支持已读、未读、全部已读和分页加载。
- 通知创建应通过数据库事务后的可靠任务执行，不能因为通知发送失败导致比分保存失败。
- 首发只实现站内消息；微信订阅消息作为后续增强能力。

## 八、客户端信息架构

### 1. 首页

- 全局搜索：球员、球队、比赛和动态。
- 官方资讯与公告。
- 近期焦点赛事。
- 校园动态信息流。
- 右下角发布按钮。
- 右上角收件箱及未读角标。

### 2. 赛程

- 按日期展示比赛。
- 区分未开始、进行中、已结束和已取消。
- 支持按赛事、阶段和球队筛选。

### 3. 数据

- 赛季和赛事切换。
- 淘汰赛晋级图。
- 小组积分榜。
- 射手榜和助攻榜。
- 明细未补全时展示数据完整度说明。

### 4. 我的

- 头像、昵称和身份标签。
- 球员认领、加入球队、个人资料和意见反馈。
- 账号与安全：修改密码、微信绑定、退出登录、账号申诉进度。
- 条件入口：球队管理、信息员工作台、质疑工单和管理员后台。

## 九、核心数据库设计

### 1. 账号与权限

```text
StudentIdentity
User
WechatBinding
UserSession
AccountAppeal
RoleAssignment
AuditLog
```

关键约束：

- `StudentIdentity.student_no` 唯一。
- 一个白名单身份最多绑定一个有效用户。
- `User.login_name_normalized` 唯一。
- 一个有效微信 `openid` 最多绑定一个用户。
- 账号占用、用户创建和微信绑定在同一事务中完成。

### 2. 赛事与球队

```text
Season
Tournament
Stage
Group
Round
RankingRule
Team
TeamRegistration
Player
PlayerClaim
RosterEntry
TeamJoinRequest
BracketSlot
AdvancementRule
```

### 3. 比赛与纠错

```text
Match
MatchEvent
MatchRevision
Dispute
DisputeAggregation
ReputationLedger
```

重要表使用软删除字段 `deleted_at`，历史版本和审计日志原则上不允许普通业务接口删除。

### 4. 社区与消息

```text
Post
Comment
Reaction
ContentReport
Notification
NotificationRecipient
NotificationAggregation
Media
```

所有表使用内部不可变主键。学号、昵称、队名等业务字段均不能作为跨表主键。

## 十、服务端与接口架构

首发采用模块化单体：

```text
微信小程序 + Web 管理端
              ↓
           REST API
              ↓
          PostgreSQL
              ↓
    对象存储 / Redis / 任务队列
```

业务模块建议：

```text
auth          注册、登录、微信绑定、会话和申诉
identity      白名单和隐私信息
tournament    赛季、赛事、赛程、积分和晋级
team          球队、球员和参赛名单
match-data    比分、事件、版本和完整度
dispute       质疑、工单和信誉
community     动态、评论、点赞和举报
notification  站内消息和聚合
admin         导入、审核、回档和审计查询
```

接口统一要求：

- 使用数据库事务保护跨表写入。
- 写接口支持幂等键，避免重复点击造成重复数据。
- 重要资源使用版本号进行乐观锁控制。
- 列表使用游标分页，避免后期数据增多时深分页变慢。
- 搜索首发可使用 PostgreSQL 索引和全文检索；数据规模明确需要时再引入独立搜索引擎。
- 缓存只用于加速，数据库始终是最终持久化来源。
- 所有重要写操作记录操作者和请求追踪 ID。

## 十一、管理后台

小程序详情页承担日常录入，但不能完全替代管理后台。首发管理后台至少支持：

- 导入和维护学生白名单。
- 创建赛季、赛事、阶段、分组、轮次和赛程。
- 批量导入球队及球员名单。
- 分配队长、信息员和赛事管理员权限。
- 查看数据完整度和待补录比赛。
- 处理账号申诉及强制下线。
- 处理聚合质疑工单。
- 查看修改历史并恢复版本。
- 发布公告并查看关键审计日志。

## 十二、实施路线

### 第一阶段：规则与基础数据

- 确定赛事规则、排名规则、比赛状态和权限矩阵。
- 完成数据库迁移、白名单导入和基础管理后台。
- 完成只读赛程、球队、球员、积分榜和淘汰赛展示。

### 第二阶段：账号闭环

- 完成姓名学号注册、密码登录、昵称登录和微信自动登录。
- 完成退出、切换账号、会话撤销及账号申诉。
- 完成球员认领和球队申请。

### 第三阶段：数据录入闭环

- 完成比分和事件的所见即所得编辑。
- 完成事件完整度提醒、并发冲突处理和版本审计。
- 完成积分、榜单和晋级关系的可靠重算。

### 第四阶段：纠错与消息

- 完成对象级质疑、聚合工单和信誉流水。
- 完成站内收件箱、未读角标和聚合通知。

### 第五阶段：社区与优化

- 完成动态、评论、点赞和举报。
- 完成长列表分页、图片压缩、缓存和性能监控。
- 根据真实运营数据决定是否增加邮箱验证、微信订阅消息、Web 用户端和独立 App。

## 十三、首发范围与暂缓内容

### 首发必须完成

- 微信小程序用户端。
- 轻量 Web 管理后台。
- 学生白名单注册、密码登录和微信绑定。
- 赛程、比分、积分榜、射手榜和淘汰赛图。
- 信息员编辑、并发保护、版本记录和质疑处理。
- 站内收件箱。
- 基础动态、评论、点赞和举报。

### 暂缓

- 强制邮箱绑定。
- 严格实名认证。
- 独立 App。
- 独立搜索引擎。
- 微服务拆分。
- 复杂的自动信誉算法。
- 仅凭质疑人数自动修改正式比分。

首发阶段允许管理员承担较多审核工作，但所有人工操作都必须结构化、可追溯。后续自动化应建立在真实运营数据之上，而不是提前写死未经验证的规则。
