# V2 工作流公共契约

> 2026-10-02 · Integrator 3 统一基线。schema、迁移、依赖锁和最终模块接线由集成负责人管理。本文补充[最终架构](晓球产品与技术架构最终版.md)，不另建技术路线。

## 1. 分工与公共依赖

- 认证分支提供 `AuthService.requireSession`、`AuthenticatedSession` 与导出的 `AccessPolicyService`；每次请求使用最新会话/角色，不另建不同口径的权限规则。
- 队长只有本队范围；赛事管理员只有授权赛事；信息员支持显式 MATCH 及 TOURNAMENT 范围。组织/平台管理员仍须有效的当前组织会话。
- 新管理路由标记 `AuthorizeInApplicationService()` 时，业务服务必须执行 fresh session + 对象策略；装饰器本身不授予权限。
- 三个旧工作树保留 WIP 后吸收已批准公共基线，不重建、不强制 reset、不互相合并 worker 分支。
- 用户明确授权的名单/排阵与信息录入 H5 功能保留。新增入口/页面有 H5 平台边界，原微信行为保留，不改首页/登录视觉。

## 2. 公共持久化

共享 schema 使用下列**确切模型**，字段/关系以 `prisma/schema.prisma` 为准：

| 模型/字段                       | 含义                                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `Match.reportVersion`           | 已保存报告的递增 CAS 版本，初始 0                                                                                                       |
| `Match.confirmedReportVersion`  | 最近官方确认版，未确认时 null；更正草稿不清除此值                                                                                       |
| `MatchReportRevision`           | 不可变的保存/提交/审核版本：组织、比赛、version、status、action、fields JSON、双方锁定 snapshot ID、ruleVersionId、真实作者、原因、时间 |
| `TeamLineupPlan`                | 团队共享的当前战术/单场阵容；name、kind、球队/组织、可选赛事/比赛/名单快照、version 与 payload                                          |
| `TeamLineupRevision`            | 不可变的显式保存版本；payload 包含当时 name/kind/tournamentId/matchId/rosterSnapshotId/lineup，不能只读当前父记录重建历史               |
| `MatchResultProjection`         | 最近确认事实的归一化结果缓存，组织+比赛唯一；sourceReportVersion、reportRevisionId、payload                                             |
| `Tournament.progressionVersion` | 晋级确认 CAS 版本，初始 0                                                                                                               |
| `TournamentProgression`         | 不可变的管理员晋级确认记录：sourceHash/sourceVersions、slots、规程版本、作者、原因                                                      |

新历史表禁止 UPDATE/DELETE；更正只能追加。测试用独立可弃数据库，不为清理 fixture 绕过不可变保护。新增 FK 保证组织隔离，业务服务还必须核对球队、赛事和快照归属。

## 3. 比赛报告

路线：`GET/POST /api/matches/:matchId/report`、`GET /api/matches/:matchId/report/history`。DTO/Swagger 由比赛报告分支实现，集成者核对；前端内部类型不得自行成为另一份公共契约。

POST 的 `clientActionId` 是幂等键，附 `expectedVersion`、`action`、`reason`；SAVE/SUBMIT/CORRECT 还附 fields 与 homeRosterSnapshotId/awayRosterSnapshotId/ruleVersionId。相同键同内容重放原结果，不产生新版本；不同内容 409。冲突不静默覆盖。

fields 保留当前 H5 数字字符串适配，服务器严格解析/界定范围；常规比分与 `homePenaltyScore/awayPenaltyScore` 分开，空字符串表示没有点球。事件用 `clientEventId`（前端非 UUID 标识），含 kind/side/minute/addedMinute/playerId/relatedPlayerId，正式确认时生成服务端 UUID。号码始终 `shirtNumber: string|null`，不能转数值丢掉 00 等标识。

| 当前状态              | 允许动作                         | 新版本与正式事实                                                              |
| --------------------- | -------------------------------- | ----------------------------------------------------------------------------- |
| 无报告/DRAFT/RETURNED | SAVE、SUBMIT                     | 追加 DRAFT/SUBMITTED，固定双方名单和规程，不改正式比分/事件                   |
| SUBMITTED             | RETURN、CONFIRM（管理员）        | 复制上一版 fields/context，追加 RETURNED/CONFIRMED；不允许审核请求偷换 fields |
| CONFIRMED             | CORRECT（管理员，原因）          | 追加新 DRAFT，旧 confirmedReportVersion/官方比分继续有效                      |
| 更正 DRAFT/RETURNED   | SAVE、SUBMIT，然后管理员 CONFIRM | 只有新 CONFIRM 才推进官方版本与投影                                           |

只有 CONFIRM 在同事务追加版本、更新 Match/正式事件、审计、Outbox。普通 FINISHED 报告对应 **Match.status=FINISHED**；`PLAYED` 只是结果引擎内部 decision，不新增 MatchStatus。ABANDONED 对应 CANCELLED/VOID，不当作双方弃权，不计官方积分或自动晋级。点球不计普通进球/射手统计。

Workspace 和历史带固定快照/规程 ID 及快照公开字段；后来的名单变化不能改写旧报告候选。缺少锁定名单/规程时明确禁止保存，不提供模拟成功。只有经确认的版本进入新正式排名；不能凭旧 FINISHED 状态猜测已审核。

## 4. 名单与阵容

赛事报名沿用 `/api/roster/tournaments/:tournamentId/teams/:teamId` 及 `/commands`，现有 RosterSubmission/Snapshot 版本模型保留。LOCK 顺序是未锁定快照→entries→只更新 lockedAt；同赛事球员不能同时锁进两队。提交/退回/批准/锁定/开放补报名必须有真实通知与审计，不能只产任务称送达。

战术路线：`GET/POST /api/captain/teams/:teamId/lineup-plans`、`GET .../:planId/revisions`。POST `{planId?,name,kind,expectedVersion,tournamentId?,matchId?,rosterSnapshotId?,payload}`，配 `Idempotency-Key`。首次 version=0，后续指定 planId/CAS，同名冲突409。

payload `{formation,format,slots:[{slotId,label,x,y,playerId}],benchPlayerIds}`。format 支持 5/7/**8**/11，x/y 是0–100百分比；首发与替补不能重复选同一球员。TACTIC 可保存无球员站位模板或本队现役成员草案；MATCH_LINEUP 必须绑定本场、本队和对应锁定名单，选人不越过快照。

服务器明确保存才增加版本。本机草稿、未保存拖拽和撤销不算云端版本；命名战术、赛事报名名单、单场阵容和官方出场统计是不同事实。阵容保存不直接改比赛出场记录。

## 5. 事件、通知与结果投影

确认事件**唯一命名**：topic=`match.report`，eventType=`MatchReportConfirmed`，aggregateType=`Match`，aggregateId=matchId。payload 必含 `{matchId,tournamentId,confirmedReportVersion,revisionId,ruleVersionId}`，可加组织/双方快照/上一确认版；dedup=`match-report-confirmed:<matchId>:<version>`。不另用 match.results/MATCH_REPORT_CONFIRMED。

Projection.payload 存归一化 ResultFact 与来源元数据：id=matchId、revision=确认版、组织/赛事/stage/group、队伍、playedAt ISO、普通/点球比分、CONFIRMED/VOID、PLAYED/弃权 decision、ruleVersionId。**不存用于公开返回的原始 notes、操作者或用户敏感字段。** Worker 读取匹配的不可变确认行，验证当前 confirmedReportVersion 后再写；旧 job 无害退出，未来版/缺行重试。不同 job 的租约 token 不替代业务版本检查。

公开汇总以当前确认版本为事实源，缓存缺失/滞后可从确认行重建，不能回显旧版。规程 JSON 使用 `CompetitionRuleVersion.rules.results`，结构为结果引擎 CompetitionRules 去掉 ruleVersionId（由数据库附上）；名单政策放 `rules.roster={minPlayers,maxPlayers,submissionDeadline,eligiblePlayerIds}`。未知规程不发明默认正式规则。历史 DEMO 展示不得声称通过新确认流程。

通知新增枚举：`ROSTER_SUBMITTED`、`ROSTER_UPDATED`、`MATCH_REPORT_SUBMITTED`、`MATCH_REPORT_REVIEWED`。名单通知 dedup=`roster:<submissionId>:<recipientUserId>`；报告 dedup=`match-report:<revisionId>:<recipientUserId>`，同事务写站内通知并产 Outbox。role 未撤销、用户 ACTIVE、当前组织 membership ACTIVE；提交通知授权审核人，结果通知对应队长/提交人。

已有 Outbox 去重键有**全局非空 partial UNIQUE**；Prisma 未表达 partial 不等于数据库无约束。本轮不重复加同名索引。Worker 可消费 roster.workflow 幂等补通知，不能重置已读；整个 job 的副作用与成功状态使用同一 SQL client 事务。

## 6. 晋级预览与确认

`POST /api/admin/tournaments/:tournamentId/progression/preview` 与 `/confirm`；服务复用 `AccessPolicyService.requireTournamentAdministrator`。公开读取在 results 模块，Experience 接线由集成者在 auth 文件交付后完成。

晋级规程使用 `rules.progression={sourceStageId,slots:[{targetMatchId,side,source}]}`。side 为 HOME/AWAY；source 为 `{type:GROUP_RANK,groupId,rank}` 或 `{type:MATCH_WINNER|MATCH_LOSER,matchId}`，不从比赛代码/名称猜规则。preview 请求 ruleVersionId；confirm 附 ruleVersionId、expectedVersion、sourceHash、Idempotency-Key 与原因。预览 sourceHash 至少包含组织/赛事/来源stage、ruleVersionId、参赛队/分组、来源场次及最新 confirmedReportVersion（未确认也纳入version0）；确认时重新计算并比较，事务更新目标签位、Tournament.progressionVersion、不可变记录、审计和Outbox。

同分未裁定、来源比赛未确认、来源版本改变、目标已开始/已结束或已有报告版本都拒绝自动改队。预览只是建议，确认不通过不能写签位；更正后的旧预览不能重放。

## 7. 验收边界

独立 PostgreSQL 覆盖真实角色、保存/重试/审核/更正、历史不可变、通知回读、旧任务逆序、晋级源改变和下游保护。H5 真实接线另做浏览器验证，纯函数/模拟接口/构建记录不能代替。测试 fixture 明示虚构规程；不写日常库、不 Seed 日常数据、不 Push、不部署、微信不做。
