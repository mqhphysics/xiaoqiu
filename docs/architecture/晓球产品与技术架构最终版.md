# 晓球产品与技术架构最终版

> 文档状态：唯一有效产品与架构基线
> 当前版本：V1.0
> 更新日期：2026-09-01
> 产品定位：面向校园足球的赛事数据、球队关注与轻社区平台

## 1. 一句话目标

让学生可以像使用一款成熟的体育应用一样，快速查看校园赛事、关注主队、认识球员、讨论比赛；让赛事工作人员可以在同一套数据上完成赛程、名单和比赛信息维护。

晓球首先交付可在浏览器体验的 H5 网站，同一套 Taro + React 代码随后构建微信小程序。管理后台和 API 负责产生两端共用的官方数据。

## 2. 首版产品边界

### 2.1 五个核心入口

| 入口 | 用户问题 | 首版必须具备 |
| --- | --- | --- |
| 首页 | 今天发生了什么？ | 分类搜索、官方资讯、焦点比赛、社区动态、点赞评论与发布入口 |
| 赛程 | 什么时候踢、结果如何？ | 日期时间线、状态筛选、比分、场地、比赛详情和事件时间轴 |
| 数据 | 谁领先、谁表现最好？ | 赛季切换、小组积分榜、淘汰赛路径、射手榜、助攻榜 |
| 主队 | 我关心的球队怎么样？ | 选择一支主队、关注其他球队、战绩、近期比赛、阵容与关键球员 |
| 我的 | 我是谁、我能做什么？ | 登录、身份与角色、关联球员、队伍管理/信息员/管理员条件入口 |

桌面 H5 使用顶部五项导航；移动 H5 和微信小程序使用底部五项 Tab。页面名称、排序和信息层级保持一致。

### 2.2 关键详情页

- 比赛详情：比分、状态、时间地点、事件时间轴、双方阵容。
- 球队详情：简介、颜色、教练/队长、战绩、赛程和完整名单。
- 球员详情：头像、号码、位置、院系年级、技术资料、简介和赛季数据。
- 动态详情：正文、作者、点赞、评论和发布时间。
- 搜索结果：球员、球队、比赛和动态四类结果。

### 2.3 首版暂不追求

- 校方统一身份认证、支付、即时聊天、视频、复杂推荐和独立原生 App。
- 生产级微信授权流程。首版使用明确标识的演示账号，之后由认证适配器替换。
- 为所有历史赛事补齐真实档案。首版以一套高完整度演示赛事验证产品。

## 3. 当前交付目标

本轮交付一套可重复生成的演示联赛，用虚构数据验证真实程序行为：

- 1 个组织、2 个赛季、至少 1 个正在进行的 8 队赛事。
- 每队 14 名完整球员，共至少 112 名球员。
- 2 个小组、完整小组赛赛程，以及半决赛、三四名决赛和决赛席位。
- 已结束、进行中、未开始、延期等不同状态的比赛。
- 已结束比赛具备比分、进球、助攻、红黄牌和出场信息。
- 官方公告、社区动态、点赞和评论。
- 普通学生、球员、队长、信息员、赛事管理员五类演示账号。
- 账号、角色、关联球员、主队和关注队伍均从数据库读取。

所有演示姓名、账号、比赛和统计必须标识为 `DEMO_FIXTURE`，不得混入用户提供文档中的学号、手机号等个人信息。用户提供的报名表只保存在被 Git 忽略的 `private-data/`，用于理解字段结构，不作为公开 Seed 数据源。

## 4. 用户与权限

| 身份 | 浏览公开数据 | 发动态/评论 | 选择主队 | 球员档案 | 队伍管理 | 比赛录入 | 赛事管理 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 未登录 | 是 | 否 | 否 | 公开字段 | 否 | 否 | 否 |
| 普通学生 | 是 | 是 | 是 | 公开字段 | 否 | 否 | 否 |
| 已关联球员 | 是 | 是 | 是 | 可进入本人档案 | 否 | 否 | 否 |
| 队长 | 是 | 是 | 是 | 本队公开档案 | 本队 | 否 | 否 |
| 信息员 | 是 | 是 | 是 | 公开字段 | 否 | 授权比赛 | 否 |
| 赛事管理员 | 是 | 是 | 是 | 审核所需字段 | 是 | 是 | 是 |

权限执行分三层：

1. Controller/Guard 校验登录和基础角色。
2. Application Service 校验球队、赛事和比赛关系。
3. Repository 查询始终附带 `organization_id`，避免跨组织读取。

前端隐藏入口只改善体验，不构成权限控制。

## 5. 系统架构

```text
浏览器 H5 / 微信小程序
  apps/mini-program  (Taro + React + TypeScript)
                 |
                 | HTTPS JSON API
                 v
统一 API
  apps/api           (NestJS + TypeScript)
                 |
                 +-- PostgreSQL / Prisma
                 +-- Transactional Outbox
                 +-- 对象存储适配器（正式环境）
                 |
异步任务
  apps/worker        (NestJS Worker)

赛事管理人员
  apps/admin-web     (React + Vite + TypeScript)
```

采用模块化单体。首版的规模、团队和部署条件都不需要微服务；模块边界仍保持清晰，未来可按实际负载拆分。

## 6. 代码模块

### 6.1 前端

```text
apps/mini-program/src/
  components/        跨页面壳层与通用控件
  features/
    product/         五入口共享类型、API Repository、会话
    schedule/        赛程分组和状态逻辑
    community/       动态、点赞和评论
  pages/
    index/           首页
    readonly-schedule/ 赛程
    data-center/     数据
    my-team/         主队
    me/              我的与登录
    readonly-match-detail/ 比赛详情
    readonly-team-detail/  球队详情
    player-detail/   球员详情
    post-detail/     动态详情
```

页面不得各自维护另一份赛事事实。所有比分、球员、榜单和账号信息通过 Repository 从 API 获取；离线演示数据必须明确显示来源，不能在 API 失败时静默伪装成线上成功。

### 6.2 API

```text
apps/api/src/
  auth/              密码演示登录、会话和当前用户
  experience/        公开首页、搜索、详情、榜单和主队聚合查询
  community/         动态、点赞和评论命令
  schedule/          赛季、赛事、赛程与发布
  roster/            报名、名单、快照和导入
  database/          Prisma 生命周期与 Seed 入口
```

Controller 只处理 HTTP；Service 负责权限、事务和业务规则；Prisma 查询集中在服务层或 Repository。高风险写操作继续保留审计、幂等和版本字段。

## 7. 核心数据关系

```text
Organization
  -> Season -> Tournament
       -> Stage -> Group / Round -> Match
       -> TeamRegistration -> Team
            -> RosterSnapshot -> PlayerProfile

Match
  -> MatchAppearance
  -> MatchEvent (goal / card / substitution)

User
  -> PasswordCredential
  -> UserSession
  -> RoleAssignment
  -> linked PlayerProfile (optional)
  -> UserTeamPreference (one primary, many followed)

Post
  -> PostLike
  -> PostComment
```

### 7.1 不可破坏的规则

- 姓名不作为球员唯一标识；演示球员使用稳定 `source_key`。
- 已锁定名单只新增新版本，不覆盖历史快照。
- 已发布比赛和球员公开接口不得返回完整学号、手机号或证明材料。
- 同一用户在同一组织最多一支主队，可关注多支球队。
- 比赛统计来自比赛事件和出场记录，不在页面中手写另一份数字。
- 正式榜单只计算符合规则的比赛状态；进行中数据明确标识为实时/暂定。

## 9. 演示数据设计

### 9.1 赛事

2026 绿茵杯使用 8 队、2 组赛制。每组 4 队单循环，前 2 名进入半决赛，之后产生决赛和三四名决赛。Seed 固定当前进度，使每次重置数据库后页面一致。

### 9.2 球员档案完整度

每位球员至少包含：

- 姓名、球衣显示名、头像占位、号码。
- 主位置、第二位置、惯用脚、身高。
- 学院/专业、入学年级、家乡和个人简介。
- 所属球队、出场、首发、分钟、进球、助攻、红黄牌。

学号仅允许使用明显虚构且脱敏的演示标识，不进入公开响应。

### 9.3 账号

演示账号与密码集中记录在 `docs/testing/演示验收手册.md`。Seed 中的密码仅供本地开发，部署到公网前必须关闭演示登录并清除这些凭据。

## 10. 前端体验规则

- 首页第一屏必须同时出现产品名、当前赛事和一场焦点比赛。
- 五个入口在桌面与移动端始终可达，导航位置稳定。
- 已赛显示比分，未赛显示时间，延期/取消显示原因。
- 所有列表具有加载、空、错误和重试状态。
- 数据页解释积分、净胜球和榜单更新时间。
- 主队页在未选择时提供明确选择流程，选择后立刻展示球队摘要。
- 我的页在未登录时就是登录界面，登录后才展示角色入口。
- 演示数据可以虚构，但不允许无响应按钮、静默 Mock 或点进详情后信息骤减。
- 移动端按钮和文字不得溢出；桌面内容最大宽度统一，避免营销式大空白。

## 11. 工程与部署

### 11.1 本地运行

```powershell
docker compose up -d postgres
pnpm --filter @xiaoqiu/api db:migrate:deploy
pnpm --filter @xiaoqiu/api db:seed
pnpm dev:api
pnpm dev:h5
```

本地 API 默认使用 `3001`，H5 使用 `10087`。浏览器访问 `http://127.0.0.1:10087/`；微信开发者工具导入 `apps/mini-program`，其配置会读取 `dist/`。管理后台按需运行 `pnpm dev:admin`。

### 11.2 质量门

- `pnpm check` 全部通过。
- 空数据库可以完成迁移和重复 Seed。
- API 集成测试连接真实 PostgreSQL，不允许静默跳过。
- H5 桌面和移动尺寸完成浏览器截图验收。
- 微信小程序构建通过，发布前再做开发者工具和真机验收。
- 日志不记录密码、令牌、完整查询参数和个人敏感字段。

## 13. V1 验收清单

1. 使用五类账号都能登录，看到不同身份和入口。
2. 首页能搜索到球员、球队、比赛和动态。
3. 至少 8 支球队，每队进入后有完整简介和 14 人名单。
4. 每位球员详情不为空，并显示来源于比赛事实的赛季数据。
5. 赛程同时显示已赛比分、进行中状态和未来比赛。
6. 比赛详情的进球事件与最终比分一致。
7. 积分榜、射手榜和助攻榜可以由 Seed 比赛重新计算得到。
8. 用户可以选择主队、关注其他球队，刷新后仍保留。
9. 登录用户可以发动态、点赞和评论，刷新后仍保留。
10. 桌面 H5 和移动 H5 无严重重叠、空白页面或无效主按钮。

这十项全部通过，才称为“第一个可以试着用的版本”。
