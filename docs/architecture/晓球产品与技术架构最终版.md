# 晓球产品与技术架构最终版

> 文档状态：唯一有效产品与架构基线
> 当前版本：V1.3（实现边界与真实赛事目标同步）
> 更新日期：2026-10-04（按用户澄清恢复 16 队参赛、8 队晋级淘汰赛）
> 产品定位：面向校园足球的赛事数据、球队关注与轻社区平台

> 当前阶段：本地H5与V2后端已集成；队长名单→信息员报告→管理员审核链已在隔离数据库自动验证，真实赛事配置、小程序运行及生产部署尚未验收。当前进度见[整体汇总](../status/整体汇总与下一阶段-2026-10-02.md)，V2规则见[公共契约](V2-工作流公共契约.md)。本文是范围/约束基线，质量门不代表已经全部通过。

## 1. 一句话目标

让学生可以像使用一款成熟的体育应用一样，快速查看校园赛事、关注主队、认识球员、讨论比赛；让赛事工作人员可以在同一套数据上完成赛程、名单和比赛信息维护。

晓球首先交付可在浏览器体验的 H5 网站，同一套 Taro + React 代码随后构建微信小程序。管理后台和 API 负责产生两端共用的官方数据。

## 2. 首版产品边界

### 2.1 五个核心入口

| 入口 | 用户问题               | 首版必须具备                                               |
| ---- | ---------------------- | ---------------------------------------------------------- |
| 首页 | 今天发生了什么？       | 分类搜索、官方资讯、焦点比赛、社区动态、点赞评论与发布入口 |
| 赛程 | 什么时候踢、结果如何？ | 日期时间线、状态筛选、比分、场地、比赛详情和事件时间轴     |
| 数据 | 谁领先、谁表现最好？   | 赛季切换、小组积分榜、淘汰赛路径、射手榜、助攻榜           |
| 主队 | 我关心的球队怎么样？   | 选择一支主队、关注其他球队、战绩、近期比赛、阵容与关键球员 |
| 我的 | 我是谁、我能做什么？   | 身份与角色、关联球员、队伍管理/信息员/管理员条件入口       |

桌面 H5 使用顶部五项导航；移动 H5 和微信小程序使用底部五项 Tab。页面名称、排序和信息层级保持一致。

登录是进入产品前的独立全屏页面，不属于“我的”页面。H5 仅提供账号入口，不允许游客浏览；登录页提供账号密码、注册、邮箱验证码占位和找回密码入口，正式客户端不显示演示账号选择器或公共密码。五入口顺序固定为：首页、赛程、居中主队入口、数据、我的。当前桌面视觉采用已确认的 D 方向装饰外框，形状不改变主队功能与顺序。右上角头像只展开账户菜单。

### 2.2 关键详情页

- 比赛详情：默认展示 1-5 星评分与观赛评论，并可切换比分战报、事件时间轴和双方阵容。
- 球队详情：简介、颜色、教练/队长、战绩、赛程和完整名单。
- 球员详情：头像、号码、位置、院系年级、技术资料、简介和赛季数据。
- 动态详情：正文、作者、点赞、评论和发布时间。
- 搜索结果：球员、球队、比赛和动态四类结果。

### 2.3 首版暂不追求

- 校方统一身份认证、支付、实时音视频聊天、视频、复杂推荐和独立原生 App。P4 已加入基础私信、通知和投诉处理，不代表生产级即时通信已完成。
- 生产级微信授权流程。首版使用明确标识的演示账号，之后由认证适配器替换。
- 为所有历史赛事补齐真实档案。首版以一套高完整度演示赛事验证产品。

## 3. 当前交付目标

本轮交付一套可重复生成的演示联赛，用虚构数据验证真实程序行为：

- 1 个组织、2 个赛季；2026 赛季 16 队、32 场公开比赛，2025 历史赛季保留 8 队、8 场。
- 当前参赛队每队 14 名球员，共 224 名参赛球员；全部球队具备锁定名单与社区成员资料。
- 四组各 4 队进行单循环，小组前两名晋级八强，随后半决赛、决赛/三四名赛；新初始化不生成十六强。演示赛制不是正式竞赛晋级规程。
- 已结束、进行中、未开始、延期等不同状态的比赛。
- 已结束比赛具备比分、进球、助攻、红黄牌和出场信息。
- 官方公告、社区动态、点赞和评论。
- 普通学生、球员、队长、信息员、赛事管理员五类演示账号。
- 独立登录/注册页、比赛评分评论，以及至少一场已结束的淘汰赛。
- 账号、角色、关联球员、主队和关注队伍均从数据库读取。

所有演示姓名、账号、比赛和统计必须标识为 `DEMO_FIXTURE`，不得混入用户提供文档中的学号、手机号等个人信息。用户提供的报名表只保存在被 Git 忽略的 `private-data/`，用于理解字段结构，不作为公开 Seed 数据源。

## 4. 用户与权限

| 身份       | 浏览公开数据 | 发动态/评论 | 选择主队 | 球员档案       | 队伍管理 | 比赛录入 | 赛事管理 |
| ---------- | ------------ | ----------- | -------- | -------------- | -------- | -------- | -------- |
| 未登录     | 否           | 否          | 否       | 需登录         | 否       | 否       | 否       |
| 普通学生   | 是           | 是          | 是       | 公开字段       | 否       | 否       | 否       |
| 已关联球员 | 是           | 是          | 是       | 可进入本人档案 | 否       | 否       | 否       |
| 队长       | 是           | 是          | 是       | 本队公开档案   | 本队     | 否       | 否       |
| 信息员     | 是           | 是          | 是       | 公开字段       | 否       | 授权比赛 | 否       |
| 赛事管理员 | 是           | 是          | 是       | 审核所需字段   | 是       | 是       | 是       |

权限执行分三层：

1. Controller/Guard 校验登录和基础角色。
2. Application Service 校验球队、赛事和比赛关系。
3. Repository 查询始终附带 `organization_id`，避免跨组织读取。

前端隐藏入口只改善体验，不构成权限控制。

`/api/public/*` 是原有公开字段路由名，当前仍需有效账号会话；健康检查和非私有媒体不属于球队/赛事数据入口。组织球队目录及 ACTIVE 成员可在未报名时显示，官方参赛名单只取批准报名的锁定快照，二者不能互相推断。私信发送继续只允许 `PLATFORM_ADMIN` 的 `PLATFORM` 身份，其他角色可读历史；展示标志不授予权限。

## 5. 系统架构

```text
浏览器 H5 / 微信小程序
  apps/mini-program  (Taro + React + TypeScript)
                 |
                 | HTTPS JSON API
                 v
统一 API
  apps/api           (NestJS + TypeScript)
                 |
                 +-- PostgreSQL / Prisma
                 +-- Transactional Outbox
                 +-- 对象存储适配器（正式环境）
                 |
异步任务
  apps/worker        (NestJS Worker；已接入V2结果/晋级与通知消费)

赛事管理人员
  apps/admin-web     (React + Vite + TypeScript)
```

采用模块化单体。首版的规模、团队和部署条件都不需要微服务；模块边界仍保持清晰，未来可按实际负载拆分。

实现边界：V2 Worker已接入指定结果/晋级和通知任务，具备重试/幂等及版本保护，并完成定向数据库验证；并非所有旧topic与外部推送都已接入，日常启动脚本尚不自动启动Worker。正式媒体存储是后续目标，目前头像/内容媒体主要落在本地文件，生产持久化未完成。

### 6.2 API

```text
apps/api/src/
  auth/              密码演示登录、会话和当前用户
  experience/        首页、搜索、详情、榜单、主队及动态互动
  social/            关注、队长管理、消息私信和投诉处理
  media/             头像上传及图片处理
  schedule/          赛季、赛事、赛程与发布
  roster/            报名、名单、快照和导入
  database/          Prisma 生命周期与 Seed 入口
```

Controller 只处理 HTTP；Service 负责权限、事务和业务规则；Prisma 查询集中在服务层或 Repository。高风险写操作继续保留审计、幂等和版本字段。

## 7. 核心数据关系

```text
Organization
  -> Season -> Tournament
       -> Stage -> Group / Round -> Match
       -> TeamRegistration -> Team
            -> RosterSnapshot -> PlayerProfile

Match
  -> MatchAppearance
  -> MatchEvent (goal / card / substitution)
  -> MatchReview (one review per user)

User
  -> PasswordCredential
  -> UserSession
  -> RoleAssignment
  -> real name / student ID / bound email (restricted)
  -> linked PlayerProfile (optional)
  -> UserTeamPreference (one primary, many followed)

Post
  -> PostLike
  -> PostComment
```

### 7.1 不可破坏的规则

- 姓名不作为球员唯一标识；演示球员使用稳定 `source_key`。
- 已锁定名单只新增新版本，不覆盖历史快照。
- 已发布比赛和球员公开接口不得返回完整学号、手机号或证明材料。
- 完整学号属于受限字段，只允许本人和本组织的授权管理员读取；管理员读取实名目录必须写入审计日志。
- 登录标识可以是用户名、昵称、真实姓名、学号或绑定邮箱。昵称/姓名重复时必须以密码匹配出唯一账号，否则拒绝登录。
- 同一用户在同一组织最多一支主队，可关注多支球队。
- 比赛统计来自比赛事件和出场记录，不在页面中手写另一份数字。
- 正式榜单只计算符合规则的比赛状态；进行中数据明确标识为实时/暂定。

## 9. 演示数据设计

### 9.1 赛事

用户澄清参赛数为 16，淘汰赛剩 8 队。演示初始化采用 A/B/C/D 四组各 4 队、每组单循环与前两名晋级，八强签位为 A1-B1、B2-D1、C1-D2、A2-C2；淘汰树从八强开始，物院一队已进入决赛，另一场半决赛待赛。小组前两名的绿色标记与八强球队集合一致。2026 赛季公开 32 场（29 场结束），2025 历史赛季保留 8 场。Seed 固定初始进度，日常启动不重新 Seed，保留测试写入；旧“八队整理”入口已停用，现有报名/比赛的恢复另行审阅。这是演示赛制，正式赛事必须使用自己的规程。

### 9.2 球员档案完整度

每位球员至少包含：

- 姓名、球衣显示名、头像占位、号码。
- 主位置、第二位置、惯用脚、身高。
- 学院/专业、入学年级、家乡和个人简介。
- 所属球队、出场、首发、分钟、进球、助攻、红黄牌。

演示学号必须明显虚构。数据库保存完整演示学号用于登录、本人资料和管理员实名目录；公开比赛、球队、球员与社区响应不得包含学号，名单类受限界面按需要显示脱敏值。

### 9.3 账号

演示账号与密码集中记录在 `docs/testing/演示验收手册.md`。Seed 中的密码仅供本地开发，部署到公网前必须关闭演示登录并清除这些凭据。

## 10. 前端体验规则

- 首页第一屏必须同时出现产品名、当前赛事和一场焦点比赛。
- 五个入口在桌面与移动端始终可达，导航位置稳定。
- 已赛显示比分，未赛显示时间，延期/取消显示原因。
- 所有列表具有加载、空、错误和重试状态。
- 数据页解释积分、净胜球和榜单更新时间。
- 主队页在未选择时提供明确选择流程，选择后立刻展示球队摘要。
- 登录使用独立页面；H5 产品页面先验证有效会话，API 不可用显示真实连接错误，不回退 Mock，登录后才展示角色入口。
- 演示数据可以虚构，但不允许无响应按钮、静默 Mock 或点进详情后信息骤减。
- 移动端按钮和文字不得溢出；桌面内容最大宽度统一，避免营销式大空白。

## 13. V1 验收清单

1. 使用五类账号都能登录，看到不同身份和入口。
2. 首页能搜索到球员、球队、比赛和动态。
3. 至少 8 支球队，每队进入后有完整简介和 14 人名单。
4. 每位球员详情不为空，并显示来源于比赛事实的赛季数据。
5. 赛程同时显示已赛比分、进行中状态和未来比赛。
6. 比赛详情的进球事件与最终比分一致。
7. 积分榜、射手榜和助攻榜可以由 Seed 比赛重新计算得到。
8. 用户可以选择主队、关注其他球队，刷新后仍保留。
9. 登录用户可以发动态、点赞和评论，刷新后仍保留。
10. 桌面 H5 和移动 H5 无严重重叠、空白页面或无效主按钮。
11. 用户名、昵称、姓名和学号均可登录；本人能查看自己的学号，普通用户不能读取实名目录，组织管理员可读取本组织完整学号且访问被审计。

这十一项全部通过，才称为“第一个可以试着用的版本”。

## 14. 真实赛事试运行前的实现边界

1. **正式权限**：auth/social 已有会话授权；赛程与名单管理员 API 仍使用 P1 开发权限头。必须接入真实会话、角色和对象范围，不能把客户端声明的角色当正式权限。
2. **真实赛事来源**：首页默认赛事与赛季列表仍耦合演示代码。正式资料进数据库后，五入口必须共享明确的真实赛事上下文；不能改演示 Seed 充当正式导入。
3. **名单流程**：已有开发期 JSON 导入、锁定快照与后台核对；队长按赛事提交、管理员退回/批准、锁定与补报流程尚未闭环。球队成员管理不等于赛事名单。
4. **报告流程**：quick-report 是 Mock 技术验证，MatchEvent/MatchAppearance 是数据底座；信息员写入真实 API、提交审核、管理员确认/更正需要正式实现。
5. **统计与晋级**：已有查询计算和淘汰树展示；正式同分、点球/弃权、确认状态、结果更正及晋级确认须按真实规程实施，不沿用演示签位假设。
6. **上线与验收**：独立试运行库、上传媒体持久化、H5 发布、HTTPS/域名、备份恢复和全角色整轮演练均需完成。当前服务健康和局部测试不能代替业务验收。
