# 身份认证与教练权限接口

Worker B 的增量基于 `cf0c21226c5de01eea5c031e44b282deff322014`。身份名单、认证申请和任职授权持久化在 PostgreSQL；H5 和管理后台调用真实 API。

## 身份、权限与展示

| 产品身份   | 后端来源                                                               | 权限范围                     |
| ---------- | ---------------------------------------------------------------------- | ---------------------------- |
| 学生       | 普通组织账号；核准学生申请可设置 `STUDENT_VERIFIED`                    | 学生认证不增加管理权限       |
| 球员       | 管理员核实后关联 `User.playerProfileId`，认证等级为 `PLAYER_CONFIRMED` | 球员身份不增加球队管理权限   |
| 队长       | `RoleAssignment.role = TEAM_CAPTAIN`                                   | 指定 `TEAM`                  |
| 教练       | 新增 `RoleAssignment.role = TEAM_COACH`                                | 只能指定 `TEAM`              |
| 信息管理员 | 既有 `MATCH_REPORTER`                                                  | 指定 `MATCH` 或 `TOURNAMENT` |
| 总管理员   | 既有 `PLATFORM_ADMIN`，`organizationId = null`                         | `PLATFORM`                   |

既有 `ORGANIZATION_ADMIN`、赛事管理员、裁判和审核员角色继续保留。组织管理员／总管理员可录入和审核本组织身份；认证申请接口不能申请或授予这两种管理员权限。管理员不能审核自己的申请。

教练任职与球员档案独立。教练批准后不会创建球员档案或球队球员关系；兼任球员要另行提交球员申请并经管理员核准。撤销教练任职只撤销该任职授予的权限，保留关联球员身份。

单一展示标志继续由既有 badge preference 逻辑选择，增加 `coach` 展示种类。权限只来自当前会话的有效角色与范围。设置或显示标志不能授予权限；教练仍不能发送私信，发送权限继续仅限平台管理员。

## 队伍 scope 契约

`GET /api/auth/me` 和登录响应中的 `user.roles` 继续返回 `{ role, scopeType, scopeId }`；本增量不更改公共 contracts 包，也不新增 `managedTeamIds` 字段。主集成可以从以下条件派生该字段：

```ts
roles
  .filter((r) => (r.role === 'TEAM_CAPTAIN' || r.role === 'TEAM_COACH') && r.scopeType === 'TEAM')
  .map((r) => r.scopeId)
```

后端按会话所属组织查找目标球队，校验其 ID 等于角色的 `scopeId`。认证与重要球队写操作在事务内重新校验有效会话、组织成员和未撤销、已生效的角色；前端缓存不是授权依据。未来生效的 `grantedAt` 不产生当前权限。

为兼容既有阵容和报名调用，`AccessPolicyService.requireTeamCaptain()` 保留名称，现允许本队队长或教练。既有 `/api/captain/teams/:teamId` 工作台、报名与阵容接口沿用该路径。SocialService 的本队管理和 ExperienceService 的球队发文策略也接受教练；入队申请通知发给有效队长和教练。阵容页面由主集成实现，本分支未修改阵容布局。

## 名单与申请

`IdentityRecord` 是管理员录入的身份来源，包含身份种类、姓名、组织、对应球队／球员／信息录入范围、创建人、关联账号、授予的 RoleAssignment、状态和版本。

`IdentityApplication` 保存申请人、申请种类、球队、原候选、核验说明、`PENDING / APPROVED / REJECTED` 状态、核实后的候选、审核人、审核时间、审核说明和版本。

按登录账号实名在本组织提示未关联、未撤销的名单／球员候选。返回仅有 `id / kind / displayName / teamId / teamName`，最多20条，不返回学号、电话、邮箱、证件或其他核验资料。候选 ID 是 `record:<UUID>` 或 `player:<UUID>`。同名多人不会自动关联，也不会自动获得角色。候选超过20条时返回 `hasMoreCandidates` 并建议主动申请。

用户可以不选候选主动申请。选择候选时，后台校验候选姓名、身份和球队；越组织、已认领或撤销的候选会拒绝。申请本身只写入待审核记录。批准必须指定管理员已核实的记录／球员档案，并填写核实依据；管理员可以为主动申请选择可靠来源，不以姓名相同作为身份确认。

同用户、组织、身份种类和球队最多一条待审核申请，应用检查与数据库部分唯一索引双重防重复。拒绝后可以重新申请；已完成的申请不可再次改变结论。球员档案不能覆盖其他账号的关联；工作人员任职不能重复关联同范围的有效角色或有效任职记录。

## API

所有接口要求真实 Bearer 会话。组织取自会话，不能通过请求体切换组织。写接口都需要 `Idempotency-Key`：8–128位字母、数字、`_ . : -`。同键同请求重放返回原结果，同键不同请求返回409。写操作使用可序列化事务并记录请求 ID 与操作者审计。

| 方法与路径                                         | 权限                 | 内容                                                                                                           |
| -------------------------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `GET /api/me/identity`                             | 当前组织成员         | `{ candidates, hasMoreCandidates, applications, teams, notice }`；本人最近100条申请，组织球队基础目录最多200条 |
| `POST /api/me/identity/applications`               | 当前组织成员         | 创建待审核申请                                                                                                 |
| `GET /api/admin/identity/applications`             | 组织管理员／总管理员 | `{ items, hasMorePending }`；先取最早200条待审核，再补最近已处理申请；查看动作有审计                           |
| `GET /api/admin/identity/records`                  | 组织管理员／总管理员 | `{ items, teams, players, tournaments, matches }`，当前组织的名单与授权对象目录                                |
| `POST /api/admin/identity/records`                 | 组织管理员／总管理员 | 录入核验名单，不自动关联账号或赋权                                                                             |
| `POST /api/admin/identity/applications/:id/review` | 组织管理员／总管理员 | 核准或拒绝；要求 `expectedVersion`                                                                             |
| `POST /api/admin/identity/records/:id/revoke`      | 组织管理员／总管理员 | 撤销记录和该记录授予的任职；要求 `expectedVersion`                                                             |

申请体：

```json
{
  "kind": "TEAM_COACH",
  "candidateId": "record:<UUID>",
  "teamId": "<本组织球队UUID>",
  "message": "请核实我的教练任职来源与本人身份"
}
```

`kind` 仅允许 `STUDENT / PLAYER / TEAM_CAPTAIN / TEAM_COACH / MATCH_REPORTER`。`candidateId` 可省略。队长／教练必须有球队，可由候选带出；`message` 去首尾空格后8–1000字。

录入体的公共字段为 `kind / displayName / reason`：姓名2–120字，原因8–1000字。队长／教练只指定 `teamId`；球员只指定 `playerProfileId`；信息管理员只指定 `scopeType = MATCH | TOURNAMENT` 和 `scopeId`；学生不指定管理范围。所有对象都必须在会话组织中。教练名单不能附带球员档案。

审核体：

```json
{
  "decision": "APPROVED",
  "expectedVersion": 1,
  "resolvedCandidateId": "record:<已核实UUID>",
  "note": "依据任职来源及本人核实结果批准申请"
}
```

拒绝使用 `decision = REJECTED`，仍要求8–1000字的说明。批准可沿用申请所选候选，也可显式指定管理员核实的对象；对象必须与申请的身份／球队一致。版本冲突、重复认领或并发决定返回409。撤销体为 `{ expectedVersion, reason }`，原因8–1000字；当前管理界面只展示队长／教练／信息管理员的任职撤销，不提供球员解绑。

写接口当前遵循 Nest POST 默认201；幂等重放仍为201。输入错误400、未登录401、无权限403、组织对象不存在404、版本／关联冲突409。客户端展示实际错误并允许重试，不回退成 mock 成功。

审计事件包括 `IDENTITY_RECORD_CREATED / IDENTITY_RECORD_REVOKED / IDENTITY_APPLICATION_CREATED / IDENTITY_APPLICATION_APPROVED / IDENTITY_APPLICATION_REJECTED / IDENTITY_APPLICATIONS_VIEWED`。审计保存操作者、角色快照、目标、请求 ID、状态／版本摘要；录入、审核和撤销原因保存在审计 reason。申请说明和审核说明保存在受权限控制的申请表，不向其他同名普通账号展示。

目录目前有大小限制：名单、球队、赛事各200条，球员／比赛各500条。认证队列已优先待审核，不会因已有大量批准记录挤掉待审核申请；更多待审核在处理前批后刷新可继续查看。若组织规模超过上述目录范围，需要主集成追加分页／搜索契约。

## H5 与统一能力接入

`IdentityCenterHost` 挂在已登录的 H5 AccountBoundary。登录读取到候选后提示确认；同一浏览器会话按用户、组织和候选集合记录已提示状态，避免普通刷新反复弹窗。“我的”始终有身份认证入口，可查看待审核／批准／拒绝状态并主动申请。刷新同时读取认证状态和 `/auth/me`，更新会话与当前“我的”角色入口。

`IdentityEntry` 基于当前有效角色展示球队管理、信息录入、管理中心。球队管理先读取真实球队 scope 和工作台，再导航到既有 my-team 页面。教练没有球员档案也能进入自己的管理范围。

主集成统一负责 `/api/me/capabilities`。认证开关遵循已确认的 `identityApplications.*` 命名，本分支不另立 capability 契约。需要主集成将该能力结果接到登录提示／认证按钮的可用状态，并接入 `IdentityEntry.actions.informationEntry` 与 `administrationEntry` 回调：启用时直接打开真实功能；未启用保持“信息录入”“管理中心”等普通按钮名称，点击提示“功能暂未开放”。当前未传回调时已经采用后者行为。能力开关不能替代 API 的真实权限校验。

新增入口和弹窗采用 H5 文件。微信 fallback 返回空组件，保留既有微信行为；共享 role 展示辅助代码增加了教练种类，未执行 weapp 构建或真机验证。

## 迁移与集成

新增迁移 `20261004120000_identity_roles`：Role 增加 `TEAM_COACH`；RoleAssignment 增加教练仅限 TEAM 的检查约束；创建身份记录和申请表、组织复合外键、状态／类型约束、版本约束与待审核部分唯一索引。它不会将任何现有普通账号升级，也不会自动关联现有球员。

主集成应用本地提交后运行 Prisma migrate deploy、generate 和常规检查。公共文件增量为 schema、新迁移、AppModule、AuthService 当前 grant 生效判断、AccessPolicyService 本队教练判断、Social／Experience／Roster 本队策略，以及 H5 AccountBoundary／My 入口、共享请求头和 badge 辅助逻辑。根 package、锁文件、contracts 和生成 API client 均未修改；无新运行时依赖。主集成合并自身角色与能力契约时需核对这些公共入口，worker A 的图片／GIF 文件未修改。
