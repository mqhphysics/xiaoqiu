## 2. 先提交，还是先推送

**建立同机工作树不需要先 push。先整理并提交一个共同基线更重要。**

| 动作                | 含义                     | 对其他工作树的影响                        |
| ------------------- | ------------------------ | ----------------------------------------- |
| 编辑/保存           | 改当前目录的文件         | 其他目录不会持续跟着变                    |
| Commit              | 保存到本地 Git 历史      | 同一仓库的其他工作树可以基于/合并这个提交 |
| Push                | 上传指定分支的提交到远端 | 用于远端备份与协作；未提交文件不会上传    |
| Merge / Cherry-pick | 把已提交成果纳入目标分支 | 需在集成位置审查冲突与回归                |

Codex 官方说明支持在创建工作树时带入所选分支的未提交变化，但不是持续同步；被 Git 忽略的本机文件还有单独复制规则。[OpenAI Docs：工作树](https://learn.chatgpt.com/docs/environments/git-worktrees)

当前 `a90c` 缺少主目录已有的一些新组件，例如设置弹窗；所以不能仅凭它和主目录都显示 `77f1a27` 就认为两边文件完全一致。新开发应记录基线提交和实际文件差异。

用户准备等本轮任务结束后推送，这个节奏合理。到时顺序建议：收齐各目录成果 → 按范围形成提交 → 指定集成分支 → 集成并验证 → 再推送选定分支。主目录当前在 `codex/h5-refinement`；在这里 commit 不会自动更新 `main`，push 该分支也不等于 main 已包含成果。

不要在任务仍写文件时盲目 `git add .`、替其他任务提交半成品、清理 worktree 或用旧文件整份覆盖新版。这里的意思是先核对归属再做对应动作，不要求停掉所有只读任务。

## 3. 工作树解决什么，又还要协调什么

| 事项             | 同一个目录多任务                           | 独立工作树                                      |
| ---------------- | ------------------------------------------ | ----------------------------------------------- |
| 文件写入         | 同时改同一文件可能覆盖；有时暂时未碰到而已 | 写入各自副本，不直接覆盖另一任务                |
| 暂存/切分支      | 共用当前目录的状态，归属容易混淆           | 有独立状态，可审阅每份成果                      |
| 最终合并         | 较难分离未提交改动                         | 可以按分支提交审查、合并，但仍可能冲突          |
| API/数据模型语义 | 需要共同约定                               | 仍需要共同约定，工作树不消除语义冲突            |
| 端口与数据库     | 可能混用                                   | 仍可能混用！目录隔离不会自动创建独立服务/数据库 |
| 依赖与生成输出   | 容易互相覆盖                               | 各工作树自己的依赖/输出；磁盘与准备成本增加     |

你的下一轮跨报名、报告、统计与界面，应优先用独立工作树。小范围依次调整一个页面可以留在主目录；不要把“目前没有明显打架”理解为并发写入已被保证安全。

运行时也要标清：网页正在连哪个工作树的 API、哪个数据库、哪个前端端口。仅做 UI 的任务可以经约定共享只读 API；会写入比赛/名单的集成测试必须用独立测试库，不能为了方便把 `TEST_DATABASE_URL` 指向日常资料库。

## 4. 推荐的下一轮流程

1. 各进行中任务交付改动、验证结果与未完成项，先固定共同基线。
2. 集成负责人统一正式权限、赛事上下文、名单版本和报告状态契约。
3. 每个任务一个工作树与命名分支，例如 `codex/roster-workflow`、`codex/match-report-workflow`；根目录公共文件依然按 AGENTS 所有权维护。
4. 每个任务卡写到具体文件，并声明依赖的接口；共享壳层、experience、schema、contracts 不安排多人同时写。
5. 每个工作树按锁文件安装依赖；本机私有资料不整份复制。环境设置单独准备，端口和测试数据库写在任务卡中。
6. 成果 commit 后，由集成负责人先审查 diff，再合并/选择提交；每合一条核心链路就验证。
7. 全流程验证通过后，再更新主使用目录与推送分支。保留未完成任务的工作树，先检查可恢复资料再做后续清理。

需要手动核对时，在相应目录运行以下只读命令：

```powershell
git branch --show-current
git status --short --branch
git worktree list
git log -1 --oneline
```

已存在的外置搜索任务建议按“完成并提交自己的改动 → 对照新版共同基线审查 → 由集成负责人解决共享文件差异”交接。本轮没有替它切分支、移动目录、合并或发送指令。
