## 分支、合并、切换及清理

当前主目录应保持 **`main`**，可运行 `git branch --show-current`确认。此前其他聊天曾在同一主目录切到登录任务分支；因此打开同一项目并不保证一直在main。今后并行任务使用独立worktree，避免互相切主目录分支。

`git switch main`只是切换当前编辑的版本；**它不会合并其他分支**。集成负责人先审阅、检查、执行merge或cherry-pick，再更新main。本次main没有独有改动，因此已集成历史能快进：main指针前进到同一提交，无须另外制造一份代码。GitHub上的main还要在Push成功后才更新。

本机现有28个分支、15个worktree（本轮盘点快照）：

| 分类     | 分支                                                                                                                                                                   | 状态                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 当前基线 | `main`                                                                                                                                                                 | 收齐成果，作为下一轮共同起点                 |
| 网站任务 | `codex/h5-refinement`、`codex/login-art-stages-1-3`、`codex/h5-home-polish`、`codex/login-cursor-assets`、`codex/login-particle-engine`、`codex/search-motion-history` | 完成提交已纳入；暂停的后续需求仍未实施       |

| 历史任务 | 12个`ai/p0-*`、`ai/p1-*`、`ai/p2-*`、`ai/p4-*`，3个`integration/*`                                                                                                     | 已属于原有开发历史，可按清理条件处理         |

完成并合入后可以删除任务分支；提交仍在main历史中，不会随分支名消失。推荐保留main和必要的近期交付标记，完成任务的worktree关闭服务后逐个清理。先确认提交已纳入且工作区干净，再 `git worktree remove <路径>`、`git branch -d <分支>`。cherry-pick分支需另外核对补丁；不能只凭名字就删除。

本轮未批量删除历史分支，尤其保留存在未提交资料的旧P4和构建检查目录。不使用强制删除规避Git保护。删除Git分支/worktree与归档Codex聊天是分别处理的事项。推送本轮main即可完整上传已集成项目，没必要把所有历史任务分支一并发布到GitHub。

## 距离第一轮真实比赛还要补哪些

目标仍是：**队长提交名单 → 信息员录入事件 → 管理员审核 → 正式结果展示**。建议下一阶段优先以下工作，而不是继续新增端口和测试专用入口。

| 优先级       | 工作                           | 完成的判据                                                                                         |
| ------------ | ------------------------------ | -------------------------------------------------------------------------------------------------- |
| P0           | 真实赛事初始化与权限配置       | 正确建立赛季/赛事/阶段/规则版本/球队报名/赛程，按比赛分配信息员；无需手写SQL修补才能走流程         |

| P0           | 官方出场、分钟及纪律规则       | 排阵与实际出场区分；换人/红黄牌、弃权、取消等结果和球员统计一致，纪律处置按正式规程                |
| P0           | H5登录/刷新/会话稳定性         | 退出再登录、重载、多标签、会话过期、慢旧请求均不会污染当前用户；生产不依赖开发组织头               |

| P1           | 服务器试运行与恢复演练         | HTTPS/API/Worker持续运行，媒体持久化、备份能恢复，权限/错误日志安全，按预期并发验证                |
| 后续独立任务 | 微信模拟器与真机               | 先解决AppID/授权，再核对同一套正式数据、触控、生命周期、登录与上传，不凭H5通过推导微信通过         |

适合下一轮并行的三块是“赛事初始化/管理配置”“官方出场与纪律”“H5会话与运营闭环”；每块独立分支/worktree，共享模型与API契约由集成负责人统一负责。服务器配置和微信另开阶段，避免把界面优化、真实赛事规则和部署混为一个无法验收的大任务。

当前产品架构仍为Taro/React H5与小程序 + React管理站 + NestJS统一API + PostgreSQL/Prisma + Outbox Worker。权威范围见[架构基线](../architecture/晓球产品与技术架构最终版.md)，V2实现约定见[公共契约](../architecture/V2-工作流公共契约.md)。本文件是当前状态与下一步安排，不替代公共模型。
