> 2026-10-01 · 按本轮代码、文档与本机只读检查整理。其他任务仍在修改代码，这是一份检查时刻的快照。

## 1. 目前到什么程度

目前已经有可体验的本地 H5 演示产品：五个入口、关键详情页、数据库与 API、账号会话、社区互动、球队管理和基本后台。公开展示比工作人员的正式比赛工作流成熟。

**还不能把当前版本当作已经通过真实赛事试运行的系统。** 比赛报告页仍是 Mock 技术原型；名单正式提交/审核、结果确认/修正、真实赛事切换和晋级处理存在关键缺口。服务器、微信开发者工具和真机也未在本轮验收。

本轮已证明的范围：

- 主目录前端 TypeScript 检查通过。
- 草稿、赛程、导航和淘汰树布局的 20 个逻辑测试通过，0 跳过；这是局部逻辑测试。
- 当前 `3001` API 的 live、ready 均 HTTP 200，ready 的数据库检查正常；`10087` H5 HTTP 200。
- 代码中可确认的页面、接口、模型和部分事务存在。

本轮未证明：完整比赛流程、跨角色浏览器写入、当前所有页面的视觉与交互、小程序构建/模拟器/真机、生产部署与恢复演练。未把旧报告的通过结果自动算作本轮验收。

表中的状态这样理解：**已有实现**指有对应代码；**部分**指有底座或展示，但未形成目标闭环；**原型**指模拟/技术验证；**待做**指当前未找到可用正式流程。每一项是否适合正式使用，还要看右侧的缺口和验收。

## 3. 当前整体架构

```text
学生/球员/队长/信息员
        ↓
Taro + React：桌面/手机 H5，之后微信小程序
        ↓ JSON API
NestJS 模块化单体
  auth / experience / social / media / schedule / roster
        ↓
PostgreSQL + Prisma：组织、账号、赛事、名单、事件、统计事实、审计

赛事管理员 → React + Vite 后台 → 同一 API 与同一数据

Outbox：部分业务已写入任务表
Worker：目前只有骨架心跳，正式消费链路待实现
生产媒体存储：当前为本地文件/示意资源，持久化或对象存储待交付
```

路线继续沿用模块化单体，不需要为了多个 AI 并行就拆微服务。数据库是赛事事实来源，客户端只负责展示与授权操作；前端隐藏按钮不是鉴权，姓名不是球员唯一 ID，锁定名单保留历史版本。

架构基线见[最终版](../architecture/晓球产品与技术架构最终版.md)。本报告记录实现与缺口，不自建另一份 API 契约或公共数据模型。

## 4. 完整真实赛事：先达到这些门槛

你选定的闭环是：真实组织/赛事与工作人员账号 → 队长提交名单 → 管理员审核锁定 → 正式赛程发布 → 信息员录入事件并提交报告 → 管理员确认 → 公开比分/统计/晋级更新 → 有原因的结果修正。

| 顺序 | 最先完成的交付 | 怎么确认真的可用 |
| --- | --- | --- |
| 0 | 固定本轮成果基线、建立独立试运行库 | 当前代码有可追溯提交；正式资料不进入演示库/Seed；旧演示仍可保留体验 |
| 1 | 正式工作人员账号与对象授权 | 普通学生不能创建赛程；队长不能提交别队名单；信息员不能改未授权比赛 |
| 2 | 真实赛事上下文与规程 | 五入口都能选中真实赛事；同分、弃权、延期、点球、晋级规则明确 |
| 3 | 队长提交—管理员审核—锁定名单 | 退回后可修订；重复提交不重复创建；锁定旧版不可被静默覆盖 |
| 4 | 信息员事件/报告—管理员确认 | 不走 Mock；事件选手来自对应锁定名单；得分与事件一致；断网/重试不重复写 |
| 5 | 统计、晋级、修正与审计 | 确认前后公开状态清楚；修正后所有相关页面一致；保留操作人和原因 |
| 6 | 一场完整演练，再整轮演练 | 至少覆盖同名、退回、延期、重复提交、并发修改、结果更正；记录负责人和结果 |
| 7 | 服务器与运行保障 | HTTPS、H5/API/媒体均可访问；备份可恢复；发布后测试通过再开放真实用户 |

数据库、接口与页面可以局部并行，但授权约定、赛事上下文、名单锁定版本、报告状态与确认规则要先由集成负责人统一。先做最小必要的这条链路，不要求把未来后台规划的所有模块一次性完成。

比赛日期、实际赛制、工作人员名单、人数/资格规则、服务器条件仍需补充。这些不会阻止先完成本次盘点，但会决定后续任务的验收内容。
