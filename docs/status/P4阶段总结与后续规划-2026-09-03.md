# 晓球 P4 阶段总结与后续规划

> 总结日期：2026-09-03。实现快照：`integration/p4-detail-polish`，截至提交 `6d6c2f6`。
>
> 本文件记录本轮成果、问题与下一步建议，不替代[产品与技术架构基线](../architecture/晓球产品与技术架构最终版.md)。后续计划尚未在本次文档任务中实施；正式赛制、身份认证和发布安排需要确认后再更新架构与任务卡。

## 1. 当前结论与产品定位

本轮完成了三个业务分支的审阅、集成与补改，将项目推进为具备真实数据库读写、多角色流程和较完整视觉体验的 H5 演示版。用户已确认本轮分支工作结束。

需要明确区分三种状态：

- **本轮 H5 开发成果已集成**：五个核心入口及账户、球队、社区等主要体验已经实现并做过定向验收。
- **小程序仅完成构建兼容性检查**：不能据此认定微信运行时、开发者工具和真机交互已经验收。
- **正式运营条件尚未满足**：真实认证、完整赛事工作流、部署与恢复演练、持续运行能力仍需后续阶段验证。代码上传不等于公网部署或生产验收，本文件不对未复核的部署状态作结论。

产品长期分工建议：小程序作为学生高频使用的主要入口；H5 继续承担公开访问、产品体验验证和大屏展示；赛事管理后台承担工作人员的复杂录入与管理。两端共享数据、规则和设计语言，不要求所有布局与交互完全一致。

## 4. 遇到的问题与处理经验

### 4.1 本轮已处理的问题

| 问题                                     | 处理方式                                                       | 经验                                             |
| ---------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------ |
| 各页面大卡片较多、动态不突出、跳转不自然 | 重排信息优先级；紧凑搜索和赛事条；发布与私信使用独立浮层       | 不能只调圆角、颜色，必须先确定用户的主要任务     |
| 队徽点击与比赛卡片点击相互干扰           | 拆分目标与事件传播，增加逻辑测试                               | 页面看起来正确，不代表点击语义正确               |
| 淘汰树连线错位                           | 根据比赛节点及晋级关系统一计算布局，单独处理三四名分支         | 避免逐条凭视觉微调固定坐标                       |
| 图片质量、尺寸与安全校验不一致           | H5 先裁剪，服务端完整解码并统一规范化；增加损坏文件等测试      | 客户端压缩不能替代服务端校验                     |
| 重复提交、审批竞争和消息通知不一致       | 补齐动作标识、事务、权限与条件更新                             | “按钮能提交”不是流程完成，需验证失败与重试       |
| 默认组件样式造成文字、头像或布局异常     | 在浏览器测量尺寸并对照截图，修正实际样式覆盖                   | 编译和类型检查发现不了全部视觉错误               |
| 最终 API 构建报返回类型无法导出          | 显式导出媒体接口使用的返回类型并重跑构建                       | 开发模式可运行不能替代正式构建                   |
| 用户照文档启动时找不到 `pnpm`            | 改用已安装依赖下可执行的 `npm --prefix` 命令，补启动脚本与文档 | 必须从用户环境验证交付，不只验证开发者自己的会话 |
| 数据库环境示例与容器默认密码不一致       | 对齐本地配置并重新验证迁移、Seed 和登录                        | 配置与操作手册也是交付的一部分                   |

关于登录故障，截图明确证明迁移与 Seed 命令没有成功执行；修复后五个账号登录成功。但由于未保留用户最初失败请求的完整证据，不能将当时“账号或密码错误”的全部原因作唯一归因。

### 4.2 当前仍需处理或验证的问题

1. **小程序头像上传存在接口匹配风险。** 当前小程序实现仅压缩选中的图片，没有完整裁剪与定尺寸处理；服务端要求正方形、64–512 像素输入并核对真实格式，因此普通原始照片仍可能被拒绝。应列为下一阶段优先修复项，而不是认定已经完成跨端上传。
2. **部分文件职责过重。** 当前主队页面约 1,255 行、社区服务约 1,082 行。需要按关注、成员、申请、通知和内容治理等职责拆分，但保持行为与接口稳定，不做无目标重写。
3. **接口契约仍需收敛。** 前端有独立的产品类型与请求映射；后续应明确公共契约来源并补契约测试，减少人工同步漂移。
4. **架构文档存在滞后。** 仍保留部分 8 队、早期功能边界和旧启动命令，而实际已有 16 队展示、私信及新启动方式。需要用确认后的决策更新基线，不应让不同文档长期互相矛盾。
5. **认证仍带演示性质。** 邮箱验证码未接真实发送与验证；仅凭实名、学号找回密码的演示接口在生产模式下已禁用，但正式替代流程尚需实现。微信身份接入、账号绑定与权限授予需要完整方案。
6. **媒体与运行保障需要生产验证。** 当前头像使用本地磁盘；需明确持久卷或对象存储、备份、恢复、容量与访问策略。已有部署或运维文档不等于实际演练通过。
7. **共享构建目录影响双端联调。** H5 与微信构建当前均使用 `dist/`，后构建可能覆盖前一端产物；下一阶段应分离产物目录并同步开发者工具与部署配置。
8. **真实赛事数据生产仍需完整验收。** 有比赛展示和部分管理基础，不代表工作人员已经能从名单维护到赛后修正独立完成一场比赛。
9. **聊天与社区治理仍需运行验证。** 需要明确消息刷新、失败重试、未读一致性及滥用处理要求；已有投诉功能不代表已有实际值守与处理制度。

### 4.3 对协作方式的总结

本轮采用三条独立业务分支：界面、赛事、账户与社区。集成负责人负责共享模型、接口、依赖锁定、跨模块修正与最终验收；临时子任务用于媒体测试、事务测试和专项审查。

适合继续保留的原则是：长期业务模块交给固定负责人；可独立验收的小任务交给临时协作；公共文件指定唯一写入者；合并结果必须重新验证，不能用任务完成报告替代集成验收。

工作量并非平均分布。跨角色流程、视觉边界与环境问题占据了较多反复验证工作；没有可靠的分项耗时或 token 统计，不作百分比归因。

## 5. 下一阶段：小程序核心体验与真实流程验证

### 5.1 阶段目标

将“小程序能编译”推进为“真实手机能稳定完成核心操作”，同时验证一条工作人员维护比赛、学生端正确看到更新的最小业务链路。

相对于现有架构中的 V2 赛事工作版、V3 微信试运行版，建议提前开展小程序真机适配，与赛事工作流交错推进，不等全部后台功能完成后才第一次检查小程序。

### 5.2 建议任务包

| 编号 | 工作方向               | 关键交付与验收条件                                                                                                                |
| ---- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| N1   | 双端开发与验收环境     | 分离 H5/微信构建产物；明确 API 地址与环境配置；全新终端可按手册启动；演示初始化与日常启动分开；必要数据库测试不得静默跳过         |
| N2   | 小程序导航、列表与状态 | 完成五入口、详情返回、滚动位置恢复、加载/空/失败状态；检查安全区、键盘遮挡、长按和触控目标；取消对鼠标右键、悬停的依赖            |
| N3   | 头像与上传适配         | 完成小程序裁剪、定尺寸、真实格式处理与上传；验证相册大图、取消、失败重试；服务端校验规则不因适配而放宽                            |
| N4   | 登录与跨端会话         | 验证退出、过期、重新登录和前后台切换；明确微信身份与已有账号/球员档案的绑定方案，不凭姓名自动覆盖档案；演示认证不得带入真实试运行 |
| N5   | 赛事工作流最小链路     | 由授权人员维护一场比赛的名单与事件、确认结果；学生端比分和榜单正确更新；修正可追溯，历史名单不被当前成员调整覆盖                  |
| N6   | 跨角色与真机回归       | 覆盖普通学生、球员/队长、信息员、管理员；验证入队申请、审批通知、评论投诉等关键流程；建立缺陷清单与回归记录                       |

N1 应先提供可靠联调环境；N2、N3 与 N5 可按文件所有权拆分推进；N4 的身份方案应尽早确定；N6 持续跟随各项交付，而不是最后集中补测。以上为责任划分建议，不代表已经启动新的并行任务。

### 5.3 本阶段退出条件

- 至少在一台 Android 和一台 iOS 真机完成核心路径，并记录设备、系统及微信版本；不能只用桌面缩窄浏览器替代。
- 看赛程、进球队、关注、评论、头像上传、返回继续浏览这条路径无阻断问题。
- 弱网、重复点击、退出重进和前后台切换不会产生重复写入、串会话或不可恢复的状态。
- 一场比赛至少完成一次工作人员侧更新到学生侧显示的真实接口闭环，不通过直接修改 Seed 代替。
- H5 主路径无回退；自动化检查、隔离数据库测试与人工真机记录齐备。
- 性能先采集基线，再在开发前约定可测阈值；本总结不虚构加载时间、并发量或工期承诺。

## 6. 后续阶段规划

### 阶段二：赛事工作版与上线准备

在最小链路基础上，完成工作人员可以实际使用的一整套流程：

- 名单导入、身份关联、资格审核与锁定快照。
- 赛程发布、延期与调整；比赛事件录入、确认及纠错。
- 统计按明确的比赛确认规则更新，能够解释修正原因并保留审计。
- 完成真实认证、已验证邮箱或其他可靠找回方式、角色授予与回收；隔离演示账号、数据和初始化脚本。
- 配置预发布环境、HTTPS、媒体持久化、日志、必要监控、备份与恢复；实际验证回滚和恢复流程。
- 明确社区投诉处理责任、权限、访问范围和私信运行要求。

退出条件：组织者、队长、信息员和管理员能够使用界面完成比赛前后全过程，不需要开发人员直接改数据库；上线基础设施有可复现的验证记录。

### 阶段三：小规模真实赛事试运行

由项目负责人选择有限范围的球队与赛事，使用真实但经授权的数据，覆盖比赛前、比赛中、比赛后，而不是仅做短时间演示。

重点观察：首次使用能否找到功能、比分更新是否及时、队长审批是否顺畅、哪些操作仍必须回到群聊求助，以及出现错误时能否及时发现和恢复。

应记录登录与关键操作失败、页面加载、重复写入、消息未读一致性、投诉处理和数据修正情况。试点球队数量、试运行日期、值守人员和验收阈值应在启动前确认。

退出条件：阻断缺陷关闭，关键数据与实际比赛一致，运营人员能独立处理常见问题，试点反馈经过至少一轮修正与回归，再决定扩大范围。

### 阶段四：持续运营与按需扩展

基于真实使用数据优化性能、消息体验、历史赛事和管理效率。此时再评估更复杂的推荐、视频、规模化聊天或服务拆分，不以增加技术复杂度作为阶段成果。

当前没有证据要求改用微服务或重写前端。优先保持模块化单体，改善职责边界、契约一致性和部署可靠性；只有实际负载或组织边界证明需要时，再调整技术架构。

## 7. 下一轮启动前需要确认的决策

1. 试点由谁组织、哪场赛事先用、哪些岗位负责维护数据与处理问题。
2. 正式比赛采用什么赛制、名单锁定规则和成绩确认规则；不能照搬本轮 16 队演示签位。
3. 学生如何登录、账号如何关联球员、队长与管理员权限由谁授予，以及哪些资料允许公开。
4. 微信体验版与预发布环境的配置由谁提供，哪些真实设备用于持续验收。
5. 下一阶段是否按 N1–N6 启动，哪些非核心功能暂不扩展，以及每项验收由谁确认。

这些决策确认前，可以继续环境核对与兼容性盘点，但不应擅自假定真实权限、导入个人信息或发布生产服务。
